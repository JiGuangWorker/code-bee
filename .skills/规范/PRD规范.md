# PRD 规范（产品需求文档）

> **适用角色：** 产品负责人 + 工程师
> **对标原则：** 《第一条 交付诚信原则》、《需求评估标准》
> **版本：** v1.0

---

## 一、PRD 的定位

PRD 不是"想法记录"，而是**开发团队与客户之间的可验收契约**。

> PRD 上写的每一条功能描述，最终必须能被测试用例验证。
> **写不出来的功能，"可验收"就是空话。**

---

## 二、PRD 模板结构

每份 PRD 必须包含以下七个部分，缺一不可：

```
# [项目名称] PRD

## 1. 背景与目标
## 2. 用户与场景
## 3. 功能范围（必须做 / 不做的边界）
## 4. 详细功能描述
## 5. 非功能性需求
## 6. 验收标准
## 7. 风险与假设
```

---

### 1. 背景与目标

| 必须回答 | 格式要求 |
|----------|----------|
| 解决什么问题？ | 一句话说清核心痛点 |
| 目标用户是谁？ | 列出具体人群，不是"所有人" |
| 成功标准是什么？ | 可量化指标（如：处理时间从 2 小时降到 5 分钟） |

**示例：**

> 中小电商客服团队在退换货高峰期，人工处理退货工单平均耗时 2 小时/单。
> 本系统目标：将工单处理时间从 **2 小时 → 5 分钟**，覆盖 80% 标准退货场景。

---

### 2. 用户与场景

用 **Who-When-Where-What** 格式描述，每个功能至少覆盖一个典型场景：

| 字段 | 说明 | 示例 |
|------|------|------|
| Who | 具体角色 | 电商售后客服 |
| When | 触发时机 | 双11退货高峰期 |
| Where | 使用环境 | PC 端后台系统 |
| What | 想达成的操作 | 批量审批标准退货申请 |

---

### 3. 功能范围

> 对标《第一条 交付诚信原则》——**先画边界，再谈实现。**

| 类型 | 说明 |
|------|------|
| ✅ Must Have | 本期必须交付，不交付 = 项目失败 |
| 🔲 Should Have | 本期尽量交付，有替代方案可延期 |
| ❌ Won't Have | 明确不做，防止范围蔓延 |

**边界示例：**

```
✅ Must Have：
  - 退货工单自动分类（标准退货 / 异常退货）
  - 标准退货一键审批

❌ Won't Have（本期）：
  - 与物流系统自动对接（下期）
  - 客服绩效统计看板（另立项）
```

---

### 4. 详细功能描述

> **所有功能描述统一采用 Given-When-Then 格式。**
> 一个功能 = N 个场景（正常场景 + 异常场景），每个场景写一个 GWT。

#### 格式

```
### 功能名称

场景 1（正常路径）：
Given：[前置条件 — 系统当前状态、已有数据]
When：[触发动作 — 用户操作或系统事件]
Then：[预期结果 — 系统响应、状态变更、用户可见变化]

场景 2（异常路径）：
Given：[前置条件]
When：[触发动作]
Then：[预期结果 — 错误提示、状态不变、补偿动作]
```

#### 示例

```
### 标准退货一键审批

场景 1（正常审批）：
Given：工单 #1001 状态为"待审批"，属于标准退货类型
When：客服点击"审批通过"按钮
Then：
  - 工单状态更新为"已通过"
  - 系统自动生成退货单号，格式为 RT+日期+序号
  - 买家收到审批通过通知（短信 + App 推送）
  - 工单列表刷新，#1001 不再显示

场景 2（工单已被他人审批）：
Given：工单 #1001 状态为"已通过"（其他客服刚审批完）
When：客服点击"审批通过"按钮
Then：
  - 页面提示"该工单已被处理，请刷新列表"
  - 工单列表自动刷新
  - 工单状态不变，不重复生成退货单号

场景 3（网络异常）：
Given：工单 #1001 状态为"待审批"，当前网络不稳定
When：客服点击"审批通过"按钮
Then：
  - 页面提示"网络异常，请重试"
  - 审批按钮恢复可点击状态
  - 工单状态保持"待审批"不变
```

---

### 5. 非功能性需求

| 维度 | 要求 | 示例指标 |
|------|------|----------|
| 性能 | 关键接口响应时间 | 工单列表加载 ≤ 2s |
| 并发 | 同时在线用户数 | 支持 200 客服同时在线 |
| 安全 | 权限与数据隔离 | 客服只能看自己分配的工单 |
| 可用性 | 系统正常运行时间 | 99.5%（月故障 ≤ 3.6h） |

---

### 6. 验收标准

> 验收标准直接复用第 4 节功能描述中的 Given-When-Then。
> PRD 的 GWT 向下传递：**开发对照写 TDD 测试，QA 对照做验收测试**，三者共享同一套 GWT 描述。

```
PRD 功能描述（GWT）  →  API Fox Mock 生成  →  TDD 单元/集成测试（GWT）  →  QA 验收用例（GWT）
     同一套场景描述，贯穿全链路，Mock 先行、测试对齐、验收一致，不翻译、不转换、不遗漏
```

---

### 7. 风险与假设

| 风险/假设 | 影响 | 应对方案 |
|-----------|------|----------|
| 假设退款接口响应稳定 | 若超时会阻塞审批 | 改为异步处理，审批通过后后台调用退款 |
| 假设客服每天处理量 ≤ 500 单 | 超出时性能可能下降 | 列表分页加载，关键查询加索引 |

## 三、PRD 评审规则

| 规则 | 说明 |
|------|------|
| ❗ 未通过评审不得进入开发 | 产品负责人主持，至少 1 名工程师参与 |
| ❗ 缺少验收标准的 PRD 视为不完整 | 直接退回，补全后再评审 |
| ❗ 功能边界不清晰不得通过 | Must/Should/Won't 必须全部明确 |
| ❗ 异常情况覆盖不足退回 | 至少列出 3 种异常场景及其处理方式 |

## 四、PRD 变更流程

```
发现问题 → 评估影响范围 → 更新 PRD（标注变更记录）→ 通知开发 + QA → 重评验收标准
```

变更记录格式：

```
---
### 变更记录

| 日期 | 版本 | 变更内容 | 变更人 |
|------|------|----------|--------|
| 2026-06-27 | v1.0 | 初版 | 张三 |
| 2026-07-01 | v1.1 | 增加异常审批场景 | 李四 |
```

## 五、PRD 与 Mock 联动

> **PRD 的最终目标不仅是"写清楚需求"，更是直接产出可调用的 API Mock。**
> **推荐工具：[API Fox](https://apifox.com/)** — 集 API 文档、Mock、调试于一体，支持从接口定义一键生成 Mock 数据。

### 核心原则

```
PRD 定稿 = Mock 就绪
```

需求文档确定的那一刻，前后端就应有一份可调用的 Mock 数据，无需等待后端接口开发完成。
PRD 中的每个 GWT 场景，本质上都在描述一次 API 交互——Mock 就是将这些场景翻译成可调用的接口。

### 工作流

```
PRD 定稿 → API Fox 定义接口 → 一键生成 Mock → 前后端并行开发
```

### Given-When-Then 到 API 的映射

| GWT 要素 | API 映射 | 示例 |
|-----------|----------|------|
| Given（前置条件） | 请求参数 / Header / 数据状态 | `ticket_id=1001`，状态为"待审批" |
| When（触发动作） | API Method + Endpoint | `POST /api/v1/tickets/{id}/approve` |
| Then（预期结果） | 响应体结构 + HTTP 状态码 | `200 { "status": "approved", ... }` |

### 示例：GWT → API Mock

```
场景（正常审批）：
Given：工单 #1001 状态为"待审批"，属于标准退货类型
When：客服点击"审批通过"按钮
Then：工单状态更新为"已通过"，系统自动生成退货单号
```

对应的 API 定义（在 API Fox 中配置后即可生成 Mock）：

- **Endpoint:** `POST /api/v1/tickets/{id}/approve`
- **Request Body:** `{ "ticket_id": "1001" }`
- **Response (200):** `{ "code": 0, "data": { "status": "approved", "return_ticket_no": "RT20260627001" } }`
- **Response (409，已被他人审批):** `{ "code": 10001, "msg": "该工单已被处理，请刷新列表" }`

### 操作步骤

1. **PRD 定稿后**，将第 4 节"详细功能描述"中的每个 GWT 场景映射为 API 接口
2. **在 API Fox 中**按场景逐一定义接口：正常响应 + 异常响应（至少覆盖 3 种异常）
3. **一键生成 Mock**，前后端各自基于 Mock 并行开发
4. **后端接口就绪后**，从 Mock 切换到真实接口（仅需修改 base URL，无需改动调用逻辑）

### 收益

| 角色 | 收益 |
|------|------|
| 前端 | 无需等待后端，Mock 到手即开发 |
| 后端 | 接口契约已明确，按 Mock 响应结构实现 |
| QA | Mock 覆盖的异常场景直接作为测试用例 |
| 产品 | GWT 描述即 Mock 定义，需求不落空 |
