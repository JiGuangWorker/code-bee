# 质量保障

> 代码写出来之后的全过程：PR 审查 → 提测把关 → 合并决策。每一道门都有硬性条件，不靠人判断。

---

## 角色行为

你不是亲自审每一行代码，而是确保三件事：**每笔 PR 被有效审查（不走过场）、提测门槛不被跳过（不合格就打回）、合并按钮不随意按下（CI 不绿 + 没人 Approve = 点不动）。**

审 PR 的第一步不是看代码写得好不好，而是对照关联 Issue 的验收标准看交付对不对。

核心规则：
- CI 不绿不进审：机器先拦一道，人只审机器拦不住的
- 审 PR 先对 Issue：打开关联 Issue → 逐条确认验收标准 → 再看代码质量
- 超时 24h 没人审的 PR，技术负责人兜底
- 提测不达标就打回，不因为赶时间放行

> **本技能的 AI 定位：** AI 读 PR diff + 关联 Issue → 按检查清单逐项分析 → 输出 Review 意见。人在 PR 页面上手动贴入意见、点 Approve 或 Request Changes。

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| PR 链接 | URL | 含 CI 状态的 Pull Request | 无链接 → 拒收 |
| 关联 Issue | Issue 编号/链接 | 该 PR 对应哪个 Issue（Issue 含验收标准） | PR 描述中必须标注 Closes #编号 |
| CI 状态 | 截图/链接 | 流水线是否全绿 | 未绿 → 不提审 |
| PR 描述 | 文档 | 含概述、变更内容、关联 PRD/Issue、测试情况 | 缺描述 → 退回补全 |
| 提测单 | 文档 | 开发自检完成的提测申请 | 缺提测单 → 拒绝提测 |

### 输出

- **AI 生成的 Review 意见**：逐项检查结果 + 问题说明 + 建议修改方式。人确认后手动贴到 PR 页面
- **提测放行结论**：放行 / 打回 + 具体原因
- **合并决策建议**：可合并 / 不可合并 + 原因（人最终执行合并）

## 三道关口

### 第一道：PR Review

#### 谁来审

| 场景 | 审核人 |
|------|--------|
| 日常功能 PR | 同组同事互审 |
| 核心模块 / 架构变更 | 技术负责人 |
| 跨模块改动 | 受影响模块的 Owner + 技术负责人 |
| 24h 无人审 | 技术负责人兜底 |

#### 审什么（检查清单）

| # | 检查项 | 具体看什么 |
|---|--------|-----------|
| 0 | **对照 Issue 验收标准** | 打开关联 Issue → 逐条确认：PR 的代码是否覆盖了 Issue 中的每一条验收标准？GWT 场景是否都实现了？异常路径是否都处理了？ |
| 1 | 业务逻辑 | 除 Issue 验收标准外，边界情况？隐含约束？关联数据一致性？ |
| 2 | 编码规范 | 命名、error 处理、并发安全是否符合 [编码规范](../规范/编码规范.md)？ |
| 3 | AI 常见错误 | 魔法数字？`any` 类型？吞 error？超长函数？ |
| 4 | 测试覆盖 | 正常路径 + 异常路径 + 边界情况都测了？ |
| 5 | 模块边界 | 是否跨模块直接调 repository？前端是否跨领域 import？ |
| 6 | 文件规模 | Go 超 500 行？TS 组件超 300 行？Hook 超 200 行？超了必须拆 |
| 7 | 性能 | 有无 N+1 查询、未加索引、不必要的重渲染？ |

> **第 0 项是前提：不对照 Issue 验收标准审 PR，等于不知道代码要干什么就开始审。**
> **如果 PR 没有关联 Issue → 直接打回，要求补上 Closes #编号。** 没有参照物的 PR 不接受。

#### 审完后

| 结论 | 含义 | 下一步 |
|------|------|--------|
| ✅ Approve | 通过 | 等待 CI 绿后合并 |
| 💬 Comment | 小问题，改完不用再审 | 开发修改后自行合并 |
| ❌ Request Changes | 必须改，改完再审 | 开发修改 → push → 重新触发 Review |

#### 一审还是多审

- 常规 PR：1 人 Approve 即可
- 涉及核心模块或安全相关：至少 1 位技术负责人 Approve
- 同一人不能自审自批

---

### 第二道：提测把关

代码写完了，开发说"可以提测了"——你不能直接信。逐项确认以下 5 项：

| # | 条件 | 怎么确认 | 不满足 |
|---|------|----------|--------|
| 1 | CI 全绿 | 看流水线状态 | 直接打回，不提测 |
| 2 | 覆盖率达标 | 看覆盖率报告 | 补齐测试再提 |
| 3 | 自测通过 | 开发提供自测记录（主流程 + 异常场景） | 补自测再提 |
| 4 | 接口文档已更新 | 对照改动的接口 | 更新文档再提 |
| 5 | 数据库变更已提交 | 检查 migration 文件 | 补 migration 再提 |

> 5 项全部满足 → 放行提测，QA 负责人接手黑盒验证。
> 任一项不满足 → 打回，告诉开发具体缺什么，不让他猜。

---

### 第三道：合并决策

合并按钮不是谁说合就合，要同时满足：

| 条件 | 说明 |
|------|------|
| CI 全绿 | 单测 + lint + 覆盖率全部通过 |
| 至少 1 人 Approve | 且不是自审自批 |
| 无待解决的 Review Thread | 所有 Review Comments 已回复或解决 |
| 已 rebase main | 无冲突 |
| PR 不超过 400 行变更 | 超过必须拆 PR |

> 以上条件全部满足 → 可合并。任一不满足 → 不可合并，告诉开发缺什么。

## 驳回处理

PR 被驳回（Request Changes）时：

| 驳回原因 | 后续动作 |
|----------|----------|
| 方案设计有误 | 与 Reviewer 重新讨论方案，必要时拉架构师确认 |
| 对需求理解有误 | 重新对齐 PRD GWT |
| 质量不达标 | 补齐测试、异常处理后重新提交 |
| 范围越界 | 拆分 PR，越界部分移除或另起 PR |

> 驳回不是否定你这个人，是否定这次的实现方式。搞清楚原因后改完重新 push 即可。

## Hotfix 流程

线上 Bug 的修复走简化但不可跳过的流程：

```
线上 P0/P1 发现
  → 从 main 拉 hotfix/<简述> 分支
  → 修复 + 自测
  → 提交 PR（仍需 Review，但优先级最高）
  → 合并到 main（Squash Merge）
  → 打 Tag v1.0.1（PATCH +1）
  → 立即上线
  → 补回归测试（不让同类 Bug 再漏）
```

| Hotfix 与正常 PR 的区别 | 正常 PR | Hotfix |
|------------------------|---------|--------|
| 分支来源 | feature/* 从 main 拉 | hotfix/* 从 main 拉 |
| PR Review | 必须，24h 内 | 必须，但最高优先级（1h 内） |
| 提测-验收链条 | 走完整流程 | 跳过，自测 + Review 通过即合 |
| 合并后动作 | 等发布窗口 | 打 Tag 后立即上线 |

> Hotfix 可以跳过提测-验收链条，但不能跳过 PR Review。紧急 ≠ 不审。

## 版本演进

Bug 被发现和修复的时机决定版本号的变化（基于 [Git规范 Semantic Versioning](../规范/Git规范.md)）：

| 场景 | 版本变化 | 说明 |
|------|----------|------|
| v1.0.0 开发中，Bug 在提测前发现 | 仍为 v1.0.0 | 没发布就不算版本 |
| v1.0.0 提测阶段发现 Bug | 仍为 v1.0.0 | 打回修完再提 |
| v1.0.0 已上线，修线上 Bug | v1.0.0 → **v1.0.1** | PATCH +1，走 hotfix |
| v1.0.0 已上线，加小功能 | v1.0.0 → **v1.1.0** | MINOR +1，PATCH 归零 |
| 接口不兼容旧版 | v1.x.x → **v2.0.0** | MAJOR +1，其余归零 |

> **版本号不是开发时标注的，是合并到 main 后打 Tag 时确定的。** 开发阶段 Issue 标注的是「目标版本」，最终 Tag 以实际合并内容为准。

## 技术实现

### 自动卡住（CI 门禁）

以下检查由 CI 流水线自动执行，不通过则无法进入 Review：

- `make lint`：golangci-lint 静态分析
- `make test-backend-unit`：后端单测 + 覆盖率
- `make check-structure`：目录结构校验
- commit message 格式校验（conventional commits）
- PR 变更行数 ≤ 400 行

### 自动发现

- **CI 失败自动通知**：流水线失败时自动通知责任人（企业微信/钉钉）
- **Review 超时提醒**：PR 超过 24h 无人审 → 自动提醒技术负责人
- **P0 Bug 阻断合并**：存在未关闭 P0/P1 Bug → 阻止合入新代码
