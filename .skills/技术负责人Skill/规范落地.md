# 规范落地

> 规范不是写一份文档扔那，是做到团队成员在不知道规范的情况下也无法违规——因为违规会被工具拦住。

---

## 角色行为

你的目标是让规范从"纸面上的约定"变成"机器执行的规则"。定一条规则，就配一条自动检查。团队违反不了，也就不需要你天天盯。

核心规则：
- 每条规范必须有对应的自动化检查，没有检查的规范等于没有规范
- 新增规则是因为出现过问题，不凭空造规则
- 发现某条规则没人会违反（编辑器自动处理了），就删掉，不养废规

> **本技能的 AI 定位：** AI 生成 `.golangci.yml`、`.conform.yaml`、`Makefile` 等配置文件内容。人复制到仓库或提 PR 合入。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| 新仓库 | URL | 需要配置规范的代码仓库 | 无仓库 → 拒收 |
| 团队反馈 | 描述 | 最近反复出现的问题类型（如"commit message 格式老是不对"） | 可选，配置更新时需提供 |

### 输出

一套配置好的规范工具链，包含：
- 分支保护规则配置
- commit message 格式校验（conform）
- 代码静态分析（golangci-lint）
- 目录结构校验（conform）
- CI 流水线门禁配置

### 校验规则

- 每项配置必须能在本地验证（如 `make lint` 能跑）
- CI 流水线必须包含所有检查项
- 配置修改后必须跑一次全量 CI 确认不会误拦

## 工作流程

### 第 1 步：分支保护规则

在 GitHub/GitLab 仓库设置中配置：

| 规则 | 配置值 | 原因 |
|------|--------|------|
| 禁止直接 push main | ✅ 开启 | 所有变更必须走 PR |
| 禁止 force push main | ✅ 开启 | 防止覆盖团队代码 |
| PR 必须通过 CI 才能合并 | ✅ 开启 | CI 不绿不能合 |
| PR 至少 1 人 Approve | ✅ 开启 | 禁止自批自合 |
| 合并前必须 rebase main | ✅ 开启 | 确保无冲突 |

---

### 第 2 步：Commit Message 校验

使用 conform 工具自动检查提交格式：

**配置 `.conform.yaml`：**

```yaml
# 提交信息格式：<type>(<scope>): <subject>
checks:
  - name: conventional-commits
    pattern: '^(feat|fix|refactor|perf|test|docs|chore|style)(\([a-z-]+\))?: .{1,50}$'
    message: |
      Commit message 格式不合规。
      正确格式：<type>(<scope>): <subject>
      示例：feat(user): add login API with JWT
```

**对应的 `.golangci.yml` 模板、`.conform.yaml` 模板、`.gokins.yaml` 模板** → 参考 `../规范/templates/` 中的 `.template` 文件。

---

### 第 3 步：代码静态分析

**Go 项目配 golangci-lint：**

```bash
# 生成默认配置
golangci-lint config

# 必须开启的检查
linters:
  enable:
    - errcheck      # 强制检查 error 返回值
    - govet         # Go 官方静态分析
    - staticcheck   # 高级静态分析
    - gosimple      # 简化代码建议
    - unused        # 未使用的变量/导入
    - revive        # 替代 golint
    - misspell      # 拼写检查
```

**Makefile 集成：**

```makefile
.PHONY: lint
lint:
	golangci-lint run ./...

.PHONY: check-structure
check-structure:
	conform enforce

.PHONY: check-all
check-all: lint check-structure
```

---

### 第 4 步：CI 流水线门禁

在 CI 配置中串联所有检查：

```yaml
# .gokins.yaml 示例
pipeline:
  stages:
    - name: lint
      script: make lint
    - name: test
      script: make test-backend-unit
    - name: check-structure
      script: make check-structure
    - name: check-commits
      script: conform enforce
```

> 顺序：先跑最快的（lint），失败了后面就不用跑了，快速反馈。

---

### 第 5 步：Tag 管理规则

版本发布时在 main 上打 Tag（基于 [Git规范 Semantic Versioning](../规范/Git规范.md)）：

| 场景 | Tag 格式 | 说明 |
|------|----------|------|
| 新功能上线 | `v1.0.0` | 初始发布，之后 PATCH +1 修 Bug，MINOR +1 加功能 |
| Hotfix 上线 | `v1.0.1` | Bug 修复，PATCH +1 |
| 功能迭代上线 | `v1.1.0` | 新功能，MINOR +1，PATCH 归零 |
| 破坏性变更 | `v2.0.0` | 不兼容旧版，MAJOR +1，其余归零 |

**Tag 操作：**

```bash
git tag -a v1.0.0 -m "feat: user registration and login"
git push origin v1.0.0
```

> **谁打 Tag：** 技术负责人或指定的发布负责人。**什么时候打：** 代码合并到 main 并通过冒烟测试后。

---

### 第 6 步：验证

配置完成后，跑一次全量 CI 确认：
- 不会误拦正常代码
- 该拦的违规确实会被拦住
- 错误提示清晰，开发能看懂自己哪里违规

## 新增 / 删除规则的决策标准

| 场景 | 操作 |
|------|------|
| 团队反复出现同一类问题（如"concurrent map writes"） | **新增规则**：golangci-lint 开启对应检查 |
| 某条规则半年内零触发 | **考虑删除**：可能是编辑器/IDE 已经自动处理了，规则变成噪音 |
| 新成员入职后频繁触发某规则 | **保留 + 补充说明**：规则有价值，但错误提示写得更清楚 |
| AI 生成的代码频繁踩的坑 | **新增规则**：在 Review 清单中补充，同时看能否用工具自动检测 |

## 技术实现

### 自动卡住

- **pre-commit hook**：提交前自动跑 `make lint`，不通过则无法 commit
- **CI 流水线**：lint → test → check-structure 串联，任一步失败则整体失败
- **分支保护**：GitHub/GitLab 原生的分支保护规则 + CI 状态检查

### 自动发现

- **规范违规趋势**：统计每条规则的触发频率，周报汇报
- **新人违规率**：新成员入职首月违规率异常偏高 → 考虑补充培训或改进错误提示

## 参考

- 本技能产出的是仓库配置，不是文档。配置完成后开发不需要查规范文档，违规时 CI 会告诉他哪里错了。
- 规范是活的：出现过问题才加规则，长期不触发就删，不搞"为了规范而规范"。
