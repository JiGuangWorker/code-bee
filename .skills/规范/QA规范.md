# QA 规范（质量保证）

> **适用角色：** 工程师 + 产品负责人
> **对标原则：** 《第一条 交付诚信原则》、《PRD 规范》
> **版本：** v1.0

---

## 一、QA 的定位

> QA 不是"开发完了找人测一下"，而是**从需求到上线的全链路质量防线**。

每一个交付节点，QA 都有对应的校验责任。

---

## 二、QA 介入节点全景

```
PRD 评审 → 技术设计评审 → 开发阶段 → 提测 → 验收 → 上线 → 线上监控
   ✅           ✅           ✅        ✅      ✅     ✅       ✅
```

| 节点 | QA 做什么 | 产出物 |
|------|----------|--------|
| PRD 评审 | 确认验收标准可测试、异常场景完整 | 评审记录 |
| 技术设计评审 | 确认设计方案覆盖非功能性需求 | 评审记录 |
| 开发阶段 | 编写测试用例，准备测试数据 | 测试用例文档 |
| 提测 | 执行测试用例，记录 Bug | 测试报告 |
| 验收 | 对照 PRD 逐条验收 | 验收报告 |
| 上线 | 线上冒烟测试 | 冒烟记录 |
| 线上监控 | 监控关键指标 | 监控报警 |

---

## 三、测试用例规范

### 3.1 用例格式

采用 **Given-When-Then** 格式，与 PRD 验收标准对齐：

```
## 用例编号：TC-[模块]-[序号]

功能：标准退货一键审批
前置条件（Given）：存在工单 #1001，状态为"待审批"
操作步骤（When）：客服点击"审批通过"按钮
预期结果（Then）：
  - 工单 #1001 状态变为"已通过"
  - 页面提示"审批成功"
  - 工单列表不显示 #1001
```

---

### 3.2 用例分类

| 类型 | 覆盖内容 | 占比要求 |
|------|----------|----------|
| ✅ 正向用例 | 主流程正常操作 | 约 40% |
| ❌ 异常用例 | 参数异常、状态异常、权限异常 | 约 30% |
| ⚠️ 边界用例 | 极限值、空值、并发操作 | 约 20% |
| 🔄 回归用例 | 已修复 Bug 的复现场景 | 约 10% |

---

### 3.3 功能测试用例矩阵

每个功能至少覆盖以下维度：

| 维度 | 必测项 | 示例 |
|------|--------|------|
| 输入校验 | 必填为空、格式错误、超长 | 邮箱格式错误 |
| 状态校验 | 前置状态不符、重复操作 | 工单已被他人审批 |
| 权限校验 | 无权限操作、越权访问 | 客服查看他人工单 |
| 数据一致性 | 操作后关联数据是否一致 | 审批后库存是否正确扣减 |
| 并发 | 多人同时操作同一条数据 | 两人同时审批同一工单 |
| 网络异常 | 超时、断网、重试 | 审批提交时网络中断 |

## 四、Bug 管理规范

### 4.1 Bug 严重等级

| 等级 | 定义 | 响应时间 | 处理策略 |
|------|------|----------|----------|
| 🔴 P0-致命 | 系统崩溃 / 数据丢失 / 安全漏洞 | 1 小时内 | 立即修复，阻塞上线 |
| 🟠 P1-严重 | 核心功能不可用 / 无替代方案 | 4 小时内 | 当天修复 |
| 🟡 P2-一般 | 功能可用但有缺陷 / 有替代方案 | 24 小时内 | 本迭代修复 |
| 🟢 P3-轻微 | 体验问题 / 文案错误 | 下迭代 | 排期修复 |

---

### 4.2 Bug 提单规范

```markdown
## Bug：[简短标题]

**严重等级：** 🔴P0 / 🟠P1 / 🟡P2 / 🟢P3
**所属模块：** [模块名]
**发现环境：** 测试环境 / 预发布 / 线上
**复现步骤：**
  1. 打开工单列表页
  2. 点击"审批"按钮
  3. 弹窗中点击"确认"
**实际结果：** 页面报错 500，刷新后工单状态未变
**预期结果：** 审批成功，工单状态变为"已通过"
**复现率：** 必现 / 偶现（3次/10次）
**截图/日志：** [附截图或日志链接]
```

---

### 4.3 P0 Bug 处理流程

```
发现 P0 → 立即通知技术负责人 → 1h 内定位 → 修复 + 测试 → 紧急上线 → 写复盘报告
```

## 五、提测标准

### 5.1 提测前置条件

> 以下条件**全部满足**，开发方可提测。缺一项 = 拒绝提测。

| 条件 | 检查方式 |
|------|----------|
| 单元测试全部通过 | CI 绿 |
| 覆盖率达标 | 覆盖率报告 |
| 自测通过（主流程 + 异常场景） | 自测记录 |
| 接口文档已更新 | 文档仓库 |
| 数据库变更已提交 migration | migration 文件 |

---

### 5.2 提测单格式

```
## 提测单

项目：[项目名]
版本：v1.0.0
提测范围：
  - 功能A：退货工单自动分类
  - 功能B：标准退货一键审批
不提测范围：
  - 物流对接（下期）
  - 绩效看板（未开发）
自测结果：✅ 通过
测试环境：http://test.example.com
数据库变更：migrations/000002_add_refund_table
```

## 六、验收标准

### 6.1 准出条件

> 对标《第一条 交付诚信原则》——**满足全部条件方可交付。**

| 条件 | 标准 |
|------|------|
| 所有 Must Have 功能通过验收 | 对照 PRD 逐条验证 |
| 无 P0/P1 未修复 Bug | 遗留 Bug 等级 ≤ P2 |
| 测试用例通过率 100% | 正向 + 异常 + 边界全部通过 |
| 非功能需求达标 | 性能、安全、并发满足 PRD 指标 |
| 客户/产品负责人签字确认 | 书面确认 |

---

### 6.2 验收报告格式

```
## 验收报告

项目：[项目名]
验收日期：2026-06-27
验收人：[产品负责人姓名]

功能验收：
| 功能 | 状态 | 备注 |
|------|------|------|
| 退货工单自动分类 | ✅ 通过 | |
| 标准退货一键审批 | ✅ 通过 | |

Bug 统计：
| 等级 | 总数 | 已修复 | 遗留 |
|------|------|--------|------|
| P0 | 0 | 0 | 0 |
| P1 | 1 | 1 | 0 |
| P2 | 3 | 3 | 0 |

验收结论：✅ 通过 / ❌ 不通过

签字：
```

## 七、线上质量监控

上线后至少监控以下指标，持续 7 天：

| 监控维度 | 指标 | 报警阈值 |
|----------|------|----------|
| 接口可用性 | 5xx 错误率 | > 1% |
| 接口响应时间 | P95 耗时 | > PRD 指标 2 倍 |
| 业务异常 | 关键操作失败率 | > 0.5% |
| 客户端异常 | JS 报错率 | > 1% |

---

## 八、QA 纪律

| 规则 | 说明 |
|------|------|
| ❗ 提测不合规直接打回 | 缺自测记录 / 单元测试不通过 = 拒绝提测 |
| ❗ P0 Bug 必须当天修复 | 不存在"下迭代处理"的 P0 |
| ❗ 验收不过不得上线 | 遗留 P0/P1 = 禁止上线 |
| ❗ 上线后必须冒烟测试 | 生产环境至少跑一遍主流程 |
| ❗ 所有 Bug 必须可复现 | 提单时提供明确的复现步骤，不可复现的不接 |
