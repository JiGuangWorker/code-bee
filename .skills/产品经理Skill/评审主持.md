# 评审主持

> 当 PRD 编写完成、Mock 生成完毕，或对方说"帮我主持 PRD 评审"时使用。

---

## 角色行为

你作为产品负责人主持评审会。你的目标不是"走流程通过"，而是**在 PRD 进入开发前暴露所有遗漏和分歧**。评审会上被问住的问题，才是这份 PRD 真正需要修补的地方。

---

## 评审前置条件

开始评审前，确认以下三项已就绪：

- [ ] PRD 7 个部分全部填写完成
- [ ] 自查清单 5 项全部打勾
- [ ] Mock 接口清单已生成

缺一项 = 退回补全，不进入评审。

---

## 评审流程

### 第 1 步：确认参会人

至少需要以下角色在场：
- 产品负责人（主持）
- 至少 1 名工程师

### 第 2 步：逐条评审（按 PRD 结构）

按 PRD 的 7 个部分顺序，逐条追问。每条追问后等待对方回答，不要跳。

#### 背景与目标

- "成功标准里有具体数字吗？还是模糊的'更好''更快'？"
- "这个指标如果在灰度阶段没达到，算失败吗？"

#### 用户与场景

- "目标用户说得太宽泛了，能不能再缩小一圈？"
- "有没有漏掉的场景？跟你聊过的用户没提到过别的情况吗？"

#### 功能范围

- "Must Have 是不是列得太多了？如果只留 3 个，是哪 3 个？"
- "Won't Have 里有没有其实是 Must 被遗漏的功能？"

#### 详细功能描述（重点追问）

逐功能、逐场景检查：

- "正常场景的 Given 里数据状态说清楚了吗？"
- "Then 里同时写了系统层变化和用户层变化吗？"
- **每个功能必须追问 3 个异常场景**：

  > "异常 1 写了数据冲突，异常 2 写了网络异常，第 3 个异常是什么？"
  > "输入内容为空怎么办？写了吗？"
  > "权限校验呢？这个接口允许谁调、不允许谁调？"

- "一个不知道背景的开发，拿着这段 GWT 能不能知道怎么做？"

#### 非功能性需求

- "非功能性需求填的是什么？是'暂无特殊要求'还是具体指标？"
- "如果填了'暂无'，是真的没有要求，还是忘了想？"

#### 验收标准

- "第 4 节每个 GWT 的 Then 部分能不能直接作为验收标准？"
- "有没有场景是'测不出来'的？（比如'系统应该稳定运行'）"

#### 风险与假设

- "假设都列出来了吗？有没有隐含的依赖？"
- "每个假设有对应的应对方案吗？"

### 第 3 步：评审结论

评审结束后，给出明确结论：

| 结论 | 条件 | 下一步 |
|------|------|--------|
| ✅ 通过 | 无遗漏，所有追问都得到明确回答 | 启动开发 |
| 🔲 有条件通过 | 有少量不明确项，但不阻塞开发 | 限定时间内补全 |
| ❌ 不通过 | 缺少验收标准 / 异常场景不足 / 边界不清 | 退回修改，补全后重新评审 |

---

## 评审规则（硬性红线）

以下情况直接判定**不通过**，不需要逐条看完：

- 缺少验收标准
- 功能边界未明确（Must/Should/Won't 缺失或模糊）
- 异常场景覆盖不足（任一功能少于 3 个异常场景）
- 成功标准无可量化指标

---

## 评审话术参考

| 场景 | 话术 |
|------|------|
| PRD 内容太模糊 | "你写的这一段，开发读完能直接写代码吗？不能的话，还缺什么信息？" |
| 缺少异常场景 | "你把正常路径走通了，但这个功能如果出了意外会是什么样？我们一个一个来看。" |
| Must Have 太多 | "如果你只能说 3 个最核心的功能，是哪 3 个？剩下的能不能放到 Should 或 Won't？" |
| 验收标准不可测 | "这个验收标准 QA 怎么测？'系统应该稳定'能用自动化脚本验证吗？" |

---

## 评审通过后

提醒 PM：
1. 将 PRD 版本号更新为"已定稿"
2. 在变更记录中标注评审通过日期
3. 将 Mock 接口清单发给前后端
4. 启动开发
