# 一致性校验

> 架构师的最后一步：校验数据结构文档与逻辑流程文档之间的一致性。校验不通过 = 技术方案不得输出。

---

## 角色行为

你的目标是校验两份文档之间**没有矛盾、没有遗漏**。不做新产出，只做交叉检查。挑出不一致，标记出来让对应子技能修正。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 |
|------|------|------|
| PRD 第 4 节（GWT 场景清单） | 文档 | 全部正常 + 异常 GWT |
| 数据结构文档 | 文档 | ER 图 + 实体定义 |
| 逻辑流程文档 | 文档 | 状态机 + 时序 + 依赖 + 事务 + 并发 |

### 输出

输出 **一致性校验报告**，包含 4 项检查：

| # | 检查项 | 检查内容 |
|---|--------|----------|
| 1 | GWT 覆盖 | 每个 GWT 场景是否被两份文档覆盖 |
| 2 | 实体交叉引用 | 逻辑流程中的实体是否在数据结构中存在 |
| 3 | 状态交叉引用 | 状态机中的状态值是否在实体定义中存在 |
| 4 | 字段类型一致性 | 同一字段在两份文档中的类型是否一致 |

### 校验规则

- GWT 覆盖率 100% → 通过
- 逻辑流程中出现但数据结构中不存在的实体 → 🔴阻塞
- 状态机中出现了实体定义中未列出的状态值 → 🔴阻塞
- 字段类型不一致 → 🔴阻塞

---

## 校验流程

### 第 1 步：GWT 覆盖检查

遍历 PRD 第 4 节每个 GWT 场景，检查是否被两份文档覆盖：

| GWT 场景 | 数据结构中有应对实体？ | 逻辑流程中有状态/时序？ | 状态 |
|----------|---------------------|----------------------|------|
| 场景1 正常审批 | ✅ ticket + refund | ✅ Approve 时序 + 状态转换 | ✅ |
| 场景2 已被他人审批 | ✅ ticket | ✅ 并发约束 409 | ✅ |
| 场景3 退款失败回退 | ✅ refund | ✅ refunding → pending | ✅ |
| … | | | |

**规则：** 任一格为空 → 🔴 遗漏。

### 第 2 步：实体交叉引用

| 逻辑流程中出现的实体 | 数据结构中是否存在 | 状态 |
|-------------------|-----------------|------|
| ticket | ✅ 实体定义 第 1 条 | ✅ |
| refund | ✅ 实体定义 第 2 条 | ✅ |
| payment | ✅ 实体定义 第 3 条 | ✅ |

**规则：** 逻辑流程中出现了数据结构中不存在的实体 → 🔴阻塞。

### 第 3 步：状态交叉引用

| 状态机状态值 | 实体 | 实体定义中有此字段？ | 状态 |
|------------|------|-------------------|------|
| pending | ticket | ✅ status 字段 | ✅ |
| approved | ticket | ✅ status 字段 | ✅ |
| refunding | refund | ✅ status 字段 | ✅ |

**规则：** 状态机中出现了实体定义中未声明的状态值 → 🔴阻塞。

### 第 4 步：字段类型一致性

| 实体.字段 | 数据结构中的类型 | 逻辑流程中的使用 | 一致？ |
|----------|---------------|---------------|--------|
| ticket.id | string | "1001"（string） | ✅ |
| ticket.status | string | "pending"（string） | ✅ |
| ticket.amount | number | ≥ 0 约束（number） | ✅ |

**规则：** 同一字段在两份文档中类型不一致 → 🔴阻塞。

## 技术实现

### 自动卡住

- **GWT 覆盖扫描**：自动提取 PRD 中所有 GWT 场景编号和数据引用，对比两份文档，遗漏 → CI 告警
- **实体名称校验**：提取逻辑流程中所有大写开头的名词，在数据结构 ER 图中搜索，不存在 → 标记
- **状态值检查**：从状态机 LaTeX 公式中提取状态集合，与数据结构实体的字段值域对比

### 自动发现

- **字段类型对比**：同一字段在数据结构（ER 图标注类型）和逻辑流程（LaTeX 公式中使用的约束类型）中的类型是否兼容
