# 自测验证

> 你觉得能跑的代码和真正能跑的代码之间，隔着一条叫"测试"的鸿沟。先验证，再提 PR。

---

## 角色行为

你不是"觉得"代码没问题就提交。你是**用证据证明代码没问题**。

Karpathy 说："修 bug 的时候，别上来就改代码。先把这个 bug'录'下来——写一个能把它稳定复现的测试用例。然后再去修。修完跑一遍，测试通过了，才算真修好了，而不是你'觉得'修好了。"

核心规则：
- 修 bug 先写复现测试，让它先红（失败），再修绿（通过）
- 别只测鸡毛蒜皮的小事，测真会在用户面前炸掉的场景
- 如果某样东西你怎么都测不了——那不是测试的问题，是代码本身设计有问题

> **本技能的 AI 定位：** AI 生成测试用例草稿（覆盖正常路径 + 异常路径 + 边界），跑测试并解读结果。人确认测试覆盖充分后提交 PR。

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| 代码变更 | diff | [代码实现](代码实现.md) 产出的变更 | 无变更 → 拒收 |
| 可验证的完成标准 | 文档 | [任务理解](任务理解.md) 产出的验收条件 | 无标准 → 拒收 |
| 测试规范 | 文档 | 项目测试规范（[后端单元测试规范](../../项目规范/后端单元测试规范.md)、[自动化测试规范](../../项目规范/自动化测试规范.md) 等） | 必须参照 |

### 输出

- 测试用例清单（覆盖正常路径 + 异常路径 + 边界条件）
- 测试执行结果（通过/失败 + 覆盖率）
- 未覆盖场景说明（哪些场景测不了、为什么、风险是什么）

## 工作流程

### 第 1 步：确认测试范围

对照 [任务理解](任务理解.md) 产出的"可验证的完成标准"和异常场景清单，确认测试要覆盖什么。

| 覆盖维度 | 要测什么 | 最低要求 |
|----------|----------|----------|
| **正常路径** | Issue 验收标准 GWT 的每一条 | 100% 覆盖 |
| **异常路径** | 输入不合法、依赖不可用、状态冲突 | 所有已识别的异常场景 |
| **边界条件** | 空值、零值、极限值、并发 | 至少覆盖最常见的 3 个边界 |
| **回归** | 本次改动是否破坏了已有功能 | 已有测试全部通过 |

### 第 2 步：Bug 修复的特殊流程

如果本次任务是修 Bug，必须走红-绿循环：

```
1. 先写复现测试（红）
   → 跑测试，确认它失败（证明你抓住了 Bug）
   → 不允许跳过这一步直接改代码
   
2. 改代码修复（绿）
   → 最小改动，让测试通过
   
3. 确认修复（绿 + 不引入新红）
   → 跑全量测试，确认没有破坏已有功能
   → 如果已有测试挂了 → 你的修复引入了新问题，回溯
```

### 第 3 步：写测试

按项目测试规范写测试代码。测试结构遵循：

```go
// Go 测试命名：Test<函数名>_<场景>_<期望>
func TestCreateUser_InvalidEmail_ReturnsError(t *testing.T) { ... }
func TestCreateUser_DuplicateEmail_ReturnsConflict(t *testing.T) { ... }
```

```typescript
// TS 测试命名：describe + it
describe('createUser', () => {
  it('should return error when email is invalid', () => { ... });
  it('should return conflict when email is duplicate', () => { ... });
});
```

### 第 4 步：跑测试

```bash
# 后端
make test-backend-unit

# 前端
make test-frontend-unit
```

### 第 5 步：解读结果

| 结果 | 含义 | 动作 |
|------|------|------|
| 全部通过 + 覆盖率达标注 | 可以提 PR | 进入提 PR 流程 |
| 有失败 | 代码有 Bug | 回到 [代码实现](代码实现.md) 修正 |
| 覆盖率不达标 | 测试不够 | 补测试用例 |
| 已有测试挂了 | 你的改动破坏了现有功能 | 修复回归问题 |
| 有些场景测不了 | 代码设计可能有问题 | 记录在 PR 描述中，标注风险 |

## 什么场景必须测

| 优先级 | 场景类型 | 示例 |
|--------|----------|------|
| P0（必测） | Issue 验收标准的每条 GWT | "用户输入合法邮箱和密码 → 注册成功" |
| P0（必测） | 输入不合法 | 空值、超长、非法格式、SQL 注入 |
| P0（必测） | 依赖不可用 | DB 挂了、第三方 API 超时 |
| P1（应测） | 并发 | 同时注册同一邮箱 → 只有一个成功 |
| P1（应测） | 幂等 | 同一请求重试 → 不重复创建 |
| P1（应测） | 边界值 | 最大/最小、刚好多一个/少一个 |
| P2（可测） | 极端性能 | 大批量数据下的响应时间 |

> **核心原则：先测用户在面前会炸的场景，再补其他。**

---

## 什么情况说明代码设计有问题

| 信号 | 问题 | 建议 |
|------|------|------|
| 写测试时需要 mock 5+ 个依赖 | 类/函数职责太多 | 拆分，单一职责 |
| 测试里需要设 10+ 行前置状态 | 被测单元的依赖太复杂 | 简化依赖关系 |
| 某个关键路径完全无法触发 | 代码缺少测试钩子 | 加接口/回调/事件 |
| 为了测试把私有方法改成公开 | 测试方式不对 | 通过公开接口间接测试 |

> "如果某样东西你怎么都测不了，别偷懒跳过——那不是测试的问题，那是代码本身设计得有问题。"

## 检查清单

提 PR 前逐项确认：

| # | 检查项 | 未满足则 |
|---|--------|----------|
| 1 | Issue 每条 GWT 都有对应测试？ | 补测试 |
| 2 | 异常路径都有对应测试？ | 对标任务理解的异常清单 |
| 3 | 边界条件（空/零/极限）至少测了常见情况？ | 补边界测试 |
| 4 | 如果是修 Bug：先写了复现测试并确认它红过？ | 不许跳过，补红-绿流程 |
| 5 | 全部测试都绿了？ | 修正失败用例 |
| 6 | 已有测试全部通过（没有引入回归）？ | 修复回归 |
| 7 | 有测不了的场景吗？写 PR 描述里说明了原因和风险吗？ | 标注风险 |
| 8 | 没有为了测试把不该公开的方法改成公开？ | 通过公开接口测 |

> 8 项全部满足 → 提交 PR。
