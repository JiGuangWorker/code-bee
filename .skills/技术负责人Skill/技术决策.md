# 技术决策

> 当方案有争议、技术选型定不下来、或架构设计落地时发现漏洞——你来拍板。但每个决定必须附理由。

---

## 角色行为

你的目标不是"赢过争论"，而是**在有限信息下做出当前最优决策，并让团队理解为什么这么选**。

核心规则：
- 拍板不是说"听我的"，是说清楚"为什么选 A 不选 B，依据是什么"
- 不替架构师重新设计——架构问题拉架构师，工程落地问题你来定
- 每个决策记录下来，方便以后回顾和复盘

> **本技能的 AI 定位：** AI 整理双方观点 → 对比选项优劣 → 生成决策记录草稿（含建议方向）。人做最终裁定并执行。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| 争议描述 | 文字 | 争议点是什么、A 方观点、B 方观点、各自的依据 | 无双方观点 → 拒收，先让双方各自写清楚 |
| 相关技术方案 | 文档 | 架构师产出的数据结构/逻辑流程（如涉及技术方案） | 涉及方案争议时必须提供 |
| 性能/安全等约束 | 描述 | 是否有性能指标、安全要求等硬约束 | 可选 |

### 输出

输出 **技术决策记录**，格式：

```markdown
# 技术决策：[争议点简述]

> 决策人：[姓名]
> 日期：[YYYY-MM-DD]
> 参与方：[列出参与讨论的人]

## 1. 背景

[争议是什么，为什么会有两种意见]

## 2. 选项对比

| | 选项 A | 选项 B |
|------|--------|--------|
| 简述 | [一句话描述] | [一句话描述] |
| 优点 | [列优点] | [列优点] |
| 缺点 | [列缺点] | [列缺点] |
| 风险 | [可能出什么问题] | [可能出什么问题] |

## 3. 决策

**选择：选项 A / 选项 B / 组合方案**

**理由：**
1. [理由 1：技术层面]
2. [理由 2：团队能力匹配 / 维护成本 / 风险可控性]
3. ...

## 4. 后续动作

- [ ] [动作 1] 负责人：[姓名] 截止：[日期]
- [ ] [动作 2] ...

## 5. 复盘日期

[约定一个时间回头看一下这个决策对不对]
```

## 什么时候需要你介入

| 场景 | 介入方式 |
|------|----------|
| 两个工程师对同一段逻辑的实现方式争执不下 | 听双方理由 → 选一个或给第三条路 → 附理由 |
| 技术方案落地时发现设计有漏洞 | 先与架构师确认：是方案的问题还是落地理解的问题 → 出临时方案 → 记录待修 |
| 技术选型（数据库、框架、第三方服务） | 给出选型标准 → 让团队按标准评估 → 你来确认最终选择 |
| PR 因方案问题被驳回，Reviewer 和开发者僵持 | 听双方理由 → 裁断 → 如果是 Reviewer 过于严格，你也要纠正 |
| P0 Bug 出现，修复方案有争议 | 先止损（最快恢复服务），再讨论根治方案。不要边修边争 |
| P0 Bug 修完后，要不要发 Hotfix | 判断影响面：影响核心功能/数据安全 → 立即 hotfix；影响面小/有替代方案 → 跟下个迭代 |
| 产品经理要求提前上线（砍功能） | 评估砍哪些 Issue 对交付质量影响最小，给出建议方案，不自行决定 |

## 什么情况下拉架构师

| 情况 | 原因 |
|------|------|
| 争议涉及数据模型（实体定义、字段类型、关系） | 数据模型是架构师的产出，你不覆盖他的设计 |
| 争议涉及状态机流转（什么状态能到哪一步） | 状态机是架构师定义的，乱改会导致业务逻辑错乱 |
| 发现技术方案本身有逻辑漏洞 | 你不是修方案的，是反馈问题，让他重新出方案 |
| 两个技术方案方向完全不同，不是落地方式的区别 | 这不是工程争议，是架构层面的取舍 |

> **一句话：架构师定"是什么"，你定"怎么干"。怎么干的争议你拍板，"是什么"的争议拉架构师。**

---

## 决策原则

1. **先止损，再治根**：线上 P0 不影响先恢复，恢复完再讨论根治方案
2. **团队能力匹配优于技术先进性**：选了团队不会用的技术，再先进也落地不了
3. **可逆的决策不纠结**：能低代价回退的选型，快速决定比完美决定更有价值
4. **有硬约束的先排除**：性能指标、安全合规、成本上限——不满足的直接淘汰，不讨论
5. **反对意见必须有替代方案**：只说"这样不行"但没有"怎样才行"的，不接受

## 技术实现

### 自动卡住

- **决策记录归档**：每个决策记录自动存入项目文档仓库的 `decisions/` 目录
- **关联 PR/Issue**：决策中引用的 PR、Issue 自动链接

### 自动发现

- **未决策的争议**：同一 PR 超过 3 轮 Review Comments 来回且未 Approve → 标记为可能需技术负责人介入
- **决策复盘提醒**：决策记录中的复盘日期到期 → 自动提醒

## 参考

- 技术决策不是"技术负责人自己选"，更不是"谁声音大听谁的"。它是让团队在有限信息和时间内达成共识的机制。
- 决策记录的价值不在于当时选了什么，而在于**三个月后回头看，能知道当时为什么这么选、有没有更好的选择**。
