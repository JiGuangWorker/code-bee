# 问题排查

> 东西坏了，去查，别猜。读完整报错、复现问题、一次只改一个地方。

---

## 角色行为

你不是凭直觉修 Bug。你是**用证据定位根因，用最小改动修复，用测试确认**。

Karpathy 说："读完整的报错和堆栈跟踪，先复现问题再动手改，一次只改一个地方。"

核心规则：
- 不读完整报错不动手
- 不复现问题不动手
- 一次只改一个地方，改完立刻验证

> **本技能的 AI 定位：** AI 读报错 + 堆栈 + 日志 → 定位根因、给出修复建议。人确认修复方案不影响其他模块后执行。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| 问题描述 | 文本 | 什么现象、什么时候出现、怎么触发 | 无描述 → 拒收 |
| 报错信息 | 日志/截图 | 完整报错 + 堆栈跟踪 | 只有"报错了"没有具体信息 → 拒收 |
| 触发条件 | 操作步骤 | 做了什么操作导致的问题 | 无法复现 → 先定位触发条件 |

### 输出

- 根因分析（不是"可能是 XX"，是"因为 XX 所以 YY"）
- 修复方案（最小改动，说明为什么只改这里）
- 验证结果（修复后测试通过，确认没有引入新问题）

## 工作流程

### 第 1 步：收集证据

不猜，先收集：

| 收集什么 | 怎么收集 | 为什么 |
|----------|----------|--------|
| 完整报错信息 | 日志系统、终端输出、浏览器控制台 | 报错信息是定位问题的第一线索 |
| 完整堆栈跟踪 | 报错附带的 stack trace | 知道调用链，找到问题源头 |
| 触发条件 | 用户描述 + 自己复现 | 知道"什么时候炸"才能"怎么修" |
| 相关代码 | 堆栈指向的文件 + 调用链上下游 | 理解代码逻辑，找根因 |

**判断标准：** 收集完你能回答——"这个报错是在什么条件下、哪一行代码、因为什么原因触发的？"

### 第 2 步：复现问题

- 按第 1 步确认的触发条件，在本地复现
- 复现不了 → 说明触发条件判断有误，回到第 1 步
- 复现成功 → 确认你抓住了问题，可以开始修

### 第 3 步：定位根因

```
表面现象 → 直接原因 → 根本原因

示例：
表面现象：用户注册返回 500
直接原因：数据库插入失败，报 duplicate key
根本原因：唯一索引建错了字段，应该是 email 却建在了 username 上
```

**常见根因类型：**

| 类型 | 表现 | 排查方向 |
|------|------|----------|
| 数据问题 | 同一输入有时正常有时异常 | 查数据库状态、并发竞争 |
| 逻辑问题 | 某类输入必现 | 查条件判断、边界处理 |
| 依赖问题 | 突然大面积报错 | 查上游服务、网络、配置 |
| 配置问题 | 某个环境正常另一个不正常 | 对比环境差异 |
| 时序问题 | 操作顺序不同结果不同 | 查异步逻辑、事件顺序 |

### 第 4 步：修复

一次只改一个地方：

| 规则 | 原因 |
|------|------|
| 每次只改一个变量 | 改完立刻验证，确认是它起的效 |
| 不改跟问题无关的代码 | 不要"顺手"重构、格式化 |
| 用最小改动修复 | 不是重写整个函数，是改那个导致 Bug 的条件 |

### 第 5 步：验证修复

遵循 [自测验证](自测验证.md) 的 Bug 修复流程：
1. 先写复现测试（红）
2. 改代码（绿）
3. 跑全量测试确认没有引入新问题

## 四种翻车模式深度识别

Karpathy 给 AI 最常见的翻车姿势起了名字。你不是只识别——你是**识别后立刻停手**。

### Kitchen Sink（修水龙头拆了整个厨房）

| 信号 | 正确动作 |
|------|----------|
| 改着改着发现动了 5+ 个文件 | 回退，只保留跟问题直接相关的改动 |
| 心里想"既然都改了，顺便把 XX 也修了吧" | 停。XX 是另一个 Issue，不混在一起 |
| 一个 PR 同时修 Bug + 重构 + 加功能 | 拆成三个 PR，分别提交 |

### Wrong Abstraction（错误抽象）

| 信号 | 正确动作 |
|------|----------|
| 同一段代码复制粘贴了 3 遍还在复制 | 第 3 次出现时提取函数/方法 |
| 写了个接口只为"以后好扩展"，但只有一个实现 | 删掉接口，直接写具体实现 |
| 抽象了一层但所有调用方都要穿透这一层才能用 | 抽象没提供价值，删掉 |

### Optimistic Path（盲目乐观）

| 信号 | 正确动作 |
|------|----------|
| 代码只处理了正常流程，异常路径全空着 | 逐条对照 [任务理解](任务理解.md) 的异常清单补齐 |
| 心里想"这个情况不太可能发生" | 写下它发生时的处理逻辑。不太可能 ≠ 不会发生 |
| 没有对网络超时、DB 不可用、用户输入非法做处理 | 加错误处理和用户提示 |

### Runaway Refactor（失控连锁）

| 信号 | 正确动作 |
|------|----------|
| 改 A 发现要改 B，改 B 发现要改 C…… | 停手。B、C 不在本次范围，记下来另起 Issue |
| 改了一个函数签名，然后改了 10 个调用方 | 判断：这个改动真的必要吗？必要时单独提 PR |
| "这个重构不做，代码没法维护了" | 重构是单独的任务，不能在修 Bug 或做功能时混着干 |

## 常见问题速查

| 问题类型 | 典型报错 | 常见根因 |
|----------|----------|----------|
| nil pointer / undefined | `panic: runtime error: invalid memory address` / `Cannot read properties of undefined` | 未初始化、未判空、异步时序 |
| 并发 map 读写 | `fatal error: concurrent map writes` | 多 goroutine 无锁操作 map |
| 数据库唯一约束冲突 | `Error 1062: Duplicate entry` | 幂等键缺失、并发写入 |
| 超时 | `context deadline exceeded` | 下游慢、没设超时、超时太短 |
| 内存泄漏 | OOM、内存持续增长 | goroutine 泄漏、大对象未释放、闭包持有引用 |
| 死锁 | 请求卡住、超时 | 锁顺序不一致、channel 死锁 |

## 检查清单

修复 Bug 时逐项确认：

| # | 检查项 | 未满足则 |
|---|--------|----------|
| 1 | 读完了完整报错和堆栈？ | 继续读 |
| 2 | 在本地复现了问题？ | 继续找触发条件 |
| 3 | 确认了根因（不是猜的，是证据链指向的）？ | 继续定位 |
| 4 | 一次只改了一个地方？ | 拆分改动 |
| 5 | 改动是最小的吗？没有"顺手"重构/格式化？ | 回退无关改动 |
| 6 | 先写了复现测试并确认它红过？ | 不许跳过 |
| 7 | 修复后全部测试通过（包括已有测试）？ | 继续修正 |
| 8 | 有没有触发四种翻车模式？ | 停手，重新评估 |
| 9 | 如果涉及数据/配置变更，记录了 migration 步骤？ | 补变更记录 |

> 9 项全部满足 → 修复完成，提交 PR。
