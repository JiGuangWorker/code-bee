# 后端单元测试规范

> **适用角色：** 后端工程师
> **适用语言：** Go
> **对标原则：** 《第一条 交付诚信原则》
> **关联规范：** [编码规范](编码规范.md)、[后端Mock与分层测试规范](后端Mock与分层测试规范.md)、[TDD规范](../需求与质量规范/TDD规范.md)
> **版本：** v1.0

---

## 一、核心原则

> **每一个公开方法，至少一个测试用例。**

单元测试的最小粒度是**方法**。方法写完，测试同步写完——不允许先写一堆方法再回头补测试。

```
源文件                          测试文件
─────────────────────────────────────────────
service.go
  func (s *Service) Create(...)  →  service_test.go
  func (s *Service) Update(...)  →    TestCreate_* (≥1 个)
  func (s *Service) Delete(...)  →    TestUpdate_* (≥1 个)
  func (s *Service) List(...)    →    TestDelete_* (≥1 个)
                                     TestList_* (≥1 个)
```

| 规则 | 说明 |
|------|------|
| ❗ 一个方法 ≥ 一个测试函数 | 无例外。公开方法没有测试 = 未完成 |
| ❗ 测试与源文件同目录 | `service_test.go` 与 `service.go` 同级 |
| ❗ 测试函数命名自解释 | `Test[方法名]_[场景]_[期望结果]` |

## 二、每个方法测什么

一个方法的测试至少覆盖以下维度：

```
                    ┌──────────────────┐
                    │  1. 正常路径       │  输入正确 → 返回预期结果
                    ├──────────────────┤
                    │  2. 参数异常       │  空值 / 零值 / 非法格式
                    ├──────────────────┤
                    │  3. 业务异常       │  重复数据 / 状态冲突 / 权限不足
                    ├──────────────────┤
                    │  4. 边界值         │  最大值 / 最小值 / 空集合
                    ├──────────────────┤
                    │  5. 依赖异常       │  依赖方返回错误 / 超时
                    └──────────────────┘
```

以 `Approve(id string) error` 为例：

```go
// 1. 正常路径
func TestApprove_ValidOrder_UpdatesStatus(t *testing.T) { ... }

// 2. 参数异常
func TestApprove_EmptyID_ReturnsError(t *testing.T) { ... }

// 3. 业务异常
func TestApprove_AlreadyApproved_ReturnsError(t *testing.T) { ... }
func TestApprove_NoPermission_ReturnsForbidden(t *testing.T) { ... }

// 4. 边界值
func TestApprove_NonExistentOrder_ReturnsNotFound(t *testing.T) { ... }

// 5. 依赖异常（Repository 查询失败）
func TestApprove_RepositoryError_ReturnsError(t *testing.T) { ... }
```

> **每个 `func` 对应一组 `Test*` 函数，按场景列出，缺一个就是覆盖不全。**

## 三、测试文件组织

```
internal/module/order/
├── handler/
│   ├── handler.go           # 源文件
│   └── handler_test.go      # handler 每个方法的测试
├── service/
│   ├── service.go
│   ├── profile.go
│   ├── service_test.go      # service.go 中方法的测试
│   └── profile_test.go      # profile.go 中方法的测试
├── repository/
│   ├── repository.go        # 接口定义
│   ├── mysql.go             # 实现
│   └── mysql_test.go        # 每个方法的测试
├── model/
│   ├── entity.go
│   └── entity_test.go       # 含逻辑的方法才需要测试（纯 struct 可选）
└── wire.go
```

| 规则 | 说明 |
|------|------|
| ❗ 一个源文件对应一个 `_test.go` | 不把多个源文件的测试塞到一个文件 |
| ❗ 测试文件 package 与源文件相同 | service_test.go → `package service` |
| ❗ 只测试含逻辑的方法 | getter/setter/纯 struct 声明不需要测试 |

## 四、测试结构：AAA 模式

每个测试函数按 **Arrange → Act → Assert** 三段式组织：

```go
func TestApprove_ValidOrder_UpdatesStatus(t *testing.T) {
    // Arrange（准备：构造输入 + 准备依赖）
    mockRepo := new(MockOrderRepo)
    order := &model.Order{ID: "1001", Status: "pending"}
    mockRepo.On("FindByID", mock.Anything, "1001").Return(order, nil)
    mockRepo.On("Update", mock.Anything, mock.Anything).Return(nil)
    svc := NewService(mockRepo)

    // Act（执行：调被测方法，只调一次）
    err := svc.Approve(context.Background(), "1001")

    // Assert（验证：结果 + 状态 + Mock 调用）
    assert.NoError(t, err)
    assert.Equal(t, "approved", order.Status)
    mockRepo.AssertExpectations(t)
}
```

| 规则 | 说明 |
|------|------|
| ❗ Arrange → Act → Assert 三段清晰 | 用空行分隔，一眼能看出三部分 |
| ❗ 一个测试只测一个场景 | 不把多个不相关的 assert 塞进同一个测试 |
| ❗ Act 只调用被测方法一次 | 不循环调用、不重复调用 |

## 五、覆盖率的正确理解

覆盖率是**底线检查**，不是目标：

| 层级 | 最低覆盖率 | 为什么不同 |
|------|-----------|-----------|
| Service 层 | **≥ 80%** | 业务逻辑集中，必须高覆盖 |
| Handler 层 | **≥ 60%** | 含参数校验和响应封装，覆盖主路径 + 异常 |
| Repository 层 | **≥ 50%** | SQL 覆盖 CRUD 主流程即可 |

> 覆盖率达不到底线 = 方法没测全。但覆盖率达标 ≠ 测好了——**场景覆盖比行覆盖更重要**。

## 六、强制规则

| 规则 | 说明 |
|------|------|
| ❗ 一个公开方法 ≥ 一个测试函数 | 无例外 |
| ❗ 每个方法至少覆盖：正常 + 异常 + 边界 | 三种场景缺一不可 |
| ❗ 测试文件与源文件一一对应 | `service.go` → `service_test.go` |
| ❗ Arrange-Act-Assert 三段清晰 | 空行分隔 |
| ❗ 一个测试只测一件事 | 不分叉、不堆砌 |
| ❗ 覆盖率低于底线不得合并 | CI 检查 |
| ❗ Mock 写法见 [后端Mock与分层测试规范](后端Mock与分层测试规范.md) | 本文件聚焦"测什么"，Mock 实现细节见该规范 |
