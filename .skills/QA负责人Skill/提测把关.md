# 提测把关

> 工位 4：代码开发完成后，由 QA 负责人检验是否满足提测条件，把关放行或打回。

---

## 角色行为

你的目标是守住提测门槛——**开发说做完了 ≠ 可以提测**。你只认证据，不认口头承诺。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| 代码仓库链接 | URL | 含 CI 状态的代码分支 | 无链接 → 拒收 |
| CI 状态 | 截图/链接 | 流水线是否全绿 | 未绿 → 直接打回 |
| 覆盖率报告 | 文件/链接 | 单测覆盖率数据 | 缺报告 → 缺一项 |
| 自测记录 | 文档 | 主流程 + 异常场景自测结果 | 无记录 → 缺一项 |
| 接口文档 | 文件/链接 | 已更新的 API 文档 | 未更新 → 缺一项 |
| DB 迁移文件 | 文件/链接 | 数据库变更脚本 | 无文件 → 缺一项 |

### 输出

输出 **提测放行单**（见下节），包含：
- 结论（✅放行 / ❌打回）
- 5 项前置条件逐条打勾
- 提测单完整性检查结果
- 未满足项及修复指引

### 校验规则

- 5 项前置条件全满足 + 提测单完整 → ✅ 放行
- 任一前置条件不满足 → ❌ 打回，附具体说明
- CI 未绿 → 不提、不问、直接打回

---

## 提测前置条件（5 项全部满足才放行）

逐项检查，缺一项 = 打回：

| # | 条件 | 检查方式 | 你的问题 |
|---|------|----------|----------|
| 1 | 单元测试全部通过 | CI 状态 | "CI 绿了吗？截图发我。" |
| 2 | 覆盖率达标 | 覆盖率报告 | "覆盖率多少？有没有关键路径没覆盖到？" |
| 3 | 自测通过 | 自测记录 | "主流程 + 异常场景你自己跑过吗？记录发我。" |
| 4 | 接口文档已更新 | 文档仓库 | "Mock 和实际接口一致吗？有变更的地方更新了没？" |
| 5 | 数据库变更已提交 | migration 文件 | "有没有改表结构？migration 文件在哪个分支？" |

```
## 1. 前置条件检查

| # | 条件 | 状态 | 证据 |
|---|------|------|------|
| 1 | 单元测试全部通过 | ✅/❌ | CI 状态 |
| 2 | 覆盖率达标（≥ 阈值） | ✅/❌ | 覆盖率 X% |
| 3 | 自测通过（含异常场景） | ✅/❌ | 自测记录 |
| 4 | 接口文档已更新 | ✅/❌ | 文档链接 |
| 5 | 数据库变更已提交 | ✅/❌ | migration 分支 |

**前置条件结论：** 全部满足 / 缺失项目 [列出]

## 3. Bug 等级定义（提测后生效）

| 等级 | 定义 | 响应时间 | 处理策略 |
|------|------|----------|----------|
| 🔴 P0-致命 | 系统崩溃 / 数据丢失 / 安全漏洞 | 1 小时内 | 立即修复，阻塞上线 |
| 🟠 P1-严重 | 核心功能不可用 / 无替代方案 | 4 小时内 | 当天修复 |
| 🟡 P2-一般 | 功能可用但有缺陷 / 有替代方案 | 24 小时内 | 本迭代修复 |
| 🟢 P3-轻微 | 体验问题 / 文案错误 | 下迭代 | 排期修复 |

## 4. 放行结论

| 结论 | 条件 | 下一步 |
|------|------|--------|
| ✅ 放行 | 5 项前置条件全部满足 + 提测单完整 | 进入测试执行阶段 |
| ❌ 打回 | 任一前置条件不满足 | 补全后重新提测 |

**本次结论：** ✅ / ❌

**打回原因：** [逐条写明哪一项不满足、需要怎么补]

---

签字：QA 负责人 ________  日期 ________
```

打回时必须逐条说明原因，不要让开发猜。

例如：
> "提测打回。第 3 项'自测通过'没有记录。你主流程和异常场景都跑过吗？把自测记录补一下再提。"

## 提测单检查（含在放行单第 2 节，此处仅供开发自检）

让开发提交提测单，检查以下内容是否完整：

```
提测单检查项：
- [ ] 项目名称 + 版本号
- [ ] 提测范围明确（哪些功能测、哪些不测）
- [ ] 不提测范围有合理说明
- [ ] 自测结果 ✅ 通过
- [ ] 测试环境地址
- [ ] 数据库变更说明
```

**未提交提测单 = 拒绝提测。**

| 结论 | 条件 | 下一步 |
|------|------|--------|
| ✅ 放行 | 5 项前置条件全部满足 + 提测单完整 | 进入测试执行阶段 |

## 技术实现

### 自动卡住

- **CI 门禁自动阻断**：[.gokins.yaml.template](../规范/templates/.gokins.yaml.template) 配置流水线门禁：golangci-lint 不通过 → 禁止合入；单测覆盖率 < 阈值 → 禁止合入；commit message 不符合 conventional format → 禁止合入
- **`.golangci.yml.template`**：代码静态检查，不通过 → CI 红线，不可进入提测
- **`.conform.yaml.template`**：提交规范检查，不合规 → 拒绝合入

### 自动发现

- **CI 失败自动通知**：流水线失败时自动通知责任人（企业微信/钉钉），无需人工盯盘
- **提测单模板校验**：自动检查提测单是否包含所有必填字段

### 参考规范

- [.gokins.yaml.template](../规范/templates/.gokins.yaml.template)（CI 流水线门禁）
- [.golangci.yml.template](../规范/templates/.golangci.yml.template)（静态检查）
- [.conform.yaml.template](../规范/templates/.conform.yaml.template)（提交规范）
- [后端单元测试规范](../规范/后端单元测试规范.md)（覆盖率阈值）
