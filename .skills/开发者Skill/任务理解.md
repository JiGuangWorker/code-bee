# 任务理解

> 拿到 Issue 后，不动手写代码。先读完、想清楚、把"做到什么程度算完成"定义成可验证的标准。

---

## 角色行为

你的目标不是快速出代码，而是**确保第一行代码写下去之前，方向是对的**。

Karpathy 说得好："模型写出烂代码最大的原因，是它根本没读你的代码库就开始动手。"「添加认证」可能是五件不同的事——把它们列出来、说明取舍。

核心规则：
- 不读完相关代码不动手
- 不列完实现计划不动手
- 不定义清楚"做完了"不动手

> **本技能的 AI 定位：** AI 读 Issue + 技术方案 + 相关代码文件 → 梳理改动范围、识别风险点、列出实现计划。人确认计划合理后进入编码阶段。

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| Issue | 编号/链接 | 含验收标准（GWT）+ 版本归属 | 无 Issue → 拒收 |
| 技术方案 | 文档 | 架构师产出的数据结构 + 逻辑流程 | 有歧义 → 先反馈再继续 |
| 代码库上下文 | 文件路径 | 需要修改的文件及其依赖关系 | 未读 → 不产出 |

### 输出

- **改动范围清单**：要改哪些文件、每个文件改什么（不是具体代码，是意图）
- **实现计划**：分几步做、每步做什么、依赖顺序
- **可验证的完成标准**：代码写到什么程度算"这活儿干完了"（不是"功能能用"，是可检查的具象条件）
- **风险点清单**：可能踩坑的地方、需要特别注意的边界条件

## 工作流程

### 第 1 步：读代码库

不扫一眼，是真的读完：

| 读什么 | 为什么 |
|--------|--------|
| 要修改的文件（完整内容） | 理解当前实现，知道改哪里 |
| 相关文件（import 链、调用链上下游） | 避免改 A 炸 B |
| 已有模式的实现样例 | 照搬已有模式，不发明新风格 |
| 项目依赖（go.mod / package.json） | 知道项目实际依赖什么，不凭空猜 |

**判断标准：** 读完你能回答——"这个项目里跟这次改动相关的代码是怎么组织的？已有的类似功能是怎么实现的？"

### 第 2 步：读 Issue 和技术方案

| 读什么 | 确认什么 |
|--------|----------|
| Issue 验收标准（GWT） | 每条 GWT 对应的代码改动是什么 |
| 技术方案的数据结构 | 本次改动涉及哪些实体/字段/关系 |
| 技术方案的逻辑流程 | 状态怎么流转、边界条件是什么 |
| 异常路径 | 方案里有没有覆盖？没覆盖的要不要补？ |

**判断标准：** 读完你能回答——"这个 Issue 到底要我改什么？验收标准是什么？"

### 第 3 步：明确完成标准

把 Issue 中可能模糊的描述翻译成可验证的条件：

| Issue 原文 | 模糊在哪 | 翻译成可验证标准 |
|-----------|----------|-----------------|
| "加个登录验证" | 什么叫"验证"？ | ① 邮箱为空 → 提示"请输入邮箱" ② 邮箱格式不对 → 提示"邮箱格式不正确" ③ 密码少于 6 位 → 提示"密码至少 6 位" ④ 三种情况都写了测试 |
| "优化列表页性能" | "优化"怎么衡量？ | ① 首次加载 < 500ms（Lighthouse 实测） ② 滚动不卡顿（60fps） ③ 列表超过 100 条时分页加载 |

如果 Issue 里找不到可验证的标准 → **停下来问技术负责人，别自己猜。**

## 检查清单

在写第一行代码之前，逐项确认：

| # | 检查项 | 未满足则 |
|---|--------|----------|
| 1 | 是否读完了要修改的所有文件？ | 继续读 |
| 2 | 是否读完了相关依赖和调用链？ | 继续读 |
| 3 | 是否理解了已有模式的写法？ | 找类似实现对照 |
| 4 | 是否逐条理解了 Issue 的验收标准？ | 不理解的标记出来问 |
| 5 | 是否确认了技术方案中涉及的数据结构和状态流转？ | 对照方案文档 |
| 6 | 是否把"做完了"翻译成了可验证的具体条件？ | 写出具象标准 |
| 7 | 是否列出了实现步骤和依赖顺序？ | 写出计划 |
| 8 | 是否识别了可能的边界条件和异常场景？ | 写出风险点 |

> 8 项全部满足 → 可以开始写代码。任一项不满足 → 继续准备，不跳过。

## 常见翻车模式

| 翻车姿势 | 表现 | 正确做法 |
|----------|------|----------|
| 扫一眼就动手 | 代码写一半发现方向错了 | 老老实实读完第 1 步的所有文件 |
| 自由发挥验收标准 | "我觉得这样应该就行了" | Issue 没写清楚就回去问 |
| 跳过分步计划 | 闷头写了一小时发现顺序搞反了 | 先列步骤，确认依赖关系 |
| 忽略异常场景 | 只考虑正常路径，没想到用户输错/网络断/服务挂 | 第 3 步明确写出所有异常场景的处理方式 |
