# PRD 入门指南

> **定位：** 理论篇 — 通过场景模拟建立直觉，理解 PRD 背后的思考路径。
> **配套阅读：** [PRD 填空模板](./PRD填空模板.md)（拿过来直接填） | [PRD 规范](./PRD规范.md)（格式标准）
> **版本：** v1.0

---

## 一、PRD 是什么

> PRD 不是"想法记录"，而是**开发团队与客户之间的可验收契约**。

两层含义：

1. **"契约"** — PRD 是产品负责人和工程师之间的约定。你写什么，工程师就做什么。写得模糊，做出来就偏。
2. **"可验收"** — PRD 里的每一条功能描述，最终必须能被测试验证。写不出来的功能，"可验收"就是空话。

一位零经验 PM 最常见的误解：**"我把想法写清楚就行了。"** 实际上，想法清楚 ≠ 可验收。PRD 的终极标准是：**工程师拿着它就知道怎么测，QA 拿着它就知道怎么验。**

---

## 二、PRD 在整体流程中的位置

```
需求捕捉 → 需求评估 → PRD 编写 → Mock 生成 → 开发（TDD） → QA 验收 → 上线
   │           │          │           │            │            │
 发现信号    打分决策   可验收契约   API Fox    GWT→测试用例   GWT→验收
```

- **上游**：需求捕捉 + 需求评估 — 决定"做不做"
- **本环节**：PRD — 决定"做成什么样才算对"
- **下游**：Mock → 开发 → QA — 全部基于 PRD 中的 GWT 场景

---

### 场景模拟：老板丢给你一句话

> 周五下午，老板走过来说："客户抱怨退货处理太慢了，你写个 PRD，下周一给我。"
>
> 你打开空白文档，完全不知道从哪下手。

**你会怎么做？**

- A. 先去问工程师这个需求能不能实现
- B. 先找几个客服聊聊他们现在怎么处理退货的
- C. 先上网搜竞品是怎么做的
- D. 先把脑子里能想到的功能列出来

---

**正确方向：B。**

PRD 的第一步永远是理解用户。在搞清楚"谁、在什么情况下、遇到什么问题"之前，不应该跳入方案。如果你选择 A，你会发现工程师会反问你一堆你答不上来的问题；选 C，你会设计出一个"看起来不错但不解决真问题"的产品；选 D，你写出来的是功能列表，不是 PRD。

**接下来你应该：** 找 3-5 个实际处理退货的客服聊一聊，观察他们的操作流程，记录他们抱怨最多的环节。然后把这些信息转化为下一节所说的"用户与场景"。

## 三、必须理解的核心概念

### 3.1 场景（Scenario）

场景 = **谁** + **在什么时候** + **在什么环境** + **做什么事**。

一条功能通常包含两类场景：

| 类型 | 说明 | 示例 |
|------|------|------|
| 正常场景（Happy Path） | 一切顺利时用户的路径 | 客服点击"审批通过"，工单状态变为"已通过" |
| 异常场景（Edge Cases） | 出意外时系统该如何响应 | 工单已被其他客服审批了 / 网络断了 / 权限不够 |

---

### 场景模拟：PRD 被评审会打回来了

> 你按老板的要求写了一版 PRD，每条功能都写了一个场景：用户打开页面 → 点按钮 → 成功完成。你觉得已经覆盖得很全了。
>
> 评审会上，工程师看完说："你这些场景全是正常的，异常情况怎么办？比如两个人同时审批同一单怎么办？用户断网了怎么办？工单状态已经被别人改了怎么办？"
>
> 你愣住了，这些问题你一个都没想过。

**问题出在哪？**

你只写了正常路径（Happy Path）。正常路径谁都知道怎么做，工程师不需要 PRD 也能猜出来。他们真正需要你来明确的，恰恰是异常分支——因为那是**分歧的来源**。

**正确做法：** 每个功能写完正常场景后，强制自己至少想出 3 个"可能出错的地方"。不知道从哪下手？从这几个方向挖：
- 权限不够
- 数据被别人抢先改了
- 网络断了 / 超时了
- 用户操作到一半想取消
- 同一条数据被多人同时操作

---

### 3.2 Given-When-Then（GWT）

| 要素 | 含义 | 对应问题 |
|------|------|----------|
| **Given** | 前置条件 | 开始前系统是什么状态？ |
| **When** | 触发动作 | 用户做了什么？ |
| **Then** | 预期结果 | 系统应该怎样响应？用户在界面上看到什么？ |

GWT 一头连接 PRD，一头连接测试用例，**全链路不翻译**。

---

### 场景模拟：工程师说你的 GWT 写得太模糊

> 你学会了写 GWT，于是交了一版：
>
> ```
> 场景 1（正常审批）：
> Given：用户登录系统
> When：用户点击审批
> Then：审批成功
> ```
>
> 工程师看完说："你这跟没写有什么区别？'审批成功'是什么意思？工单状态变不变？要不要生成退货单号？用户界面发生什么变化？"
>
> 你被问得哑口无言。

**问题出在哪？**

GWT 的三个要素都太模糊了：

| 要素 | 你写的（❌） | 应该写的（✅） |
|------|-------------|---------------|
| Given | "用户登录系统" | "工单 #1001 状态为'待审批'，属于标准退货类型" |
| When | "用户点击审批" | "客服点击'审批通过'按钮" |
| Then | "审批成功" | "工单状态更新为'已通过'；系统自动生成退货单号 RT20260627001；工单列表刷新，#1001 不再显示" |

**GWT 的自我检验方法：** 写完之后问自己——"一个不知道需求背景的 QA，拿着这段描述能不能写出测试用例？"如果不能，说明你没写清楚。

---

### 场景模拟：开发到一半有人要加功能

> PRD 评审通过了，开发进行到第二周。你的同事突然说："诶，能不能顺便加一个批量审批？这样客服一次能审批十条，效率更高。"
>
> 你觉得有道理，跑去跟工程师说。工程师脸黑了："你 PRD 上没写，现在插进来顺序全乱了。"
>
> 你想辩解"这个需求确实很重要啊"，但你自己也不确定这是不是真的"必须本期做"。

**问题出在哪？**

PRD 没有画清楚功能边界。如果你在第 3 节明确写了"批量审批 = Should Have（有替代方案，可下期做）"，当同事提出这个需求时，你可以直接回复："这个在 PRD 里标记为 Should Have，本期不强制交付，我们排下期。"

但如果 Must / Should / Won't 没有区分清楚，所有需求看起来都"很重要"，你就永远在被牵着走。

**功能边界的判断标准：**

| 类型 | 判断问题 | 示例 |
|------|----------|------|
| ✅ Must Have | 没有这个功能，用户的目标能否达成？ | 没有"审批"按钮，客服无法完成退货处理 |
| 🔲 Should Have | 有更好，但没它用户有替代方案吗？ | 没有批量审批，客服可以逐条审批（只是慢一点） |
| ❌ Won't Have | 这个功能能不能明确推到下期？ | 物流对接——跟本期退货审批没有直接依赖关系 |

---

### 3.3 验收标准

验收标准回答：**"到什么时候可以说这个功能做完了？"**

验收标准不是另写一套文档，而是直接复用第 4 节的功能描述（GWT）。因为 GWT 已经精确描述了"系统应该怎样响应"，那就是验收的标准。

---

### 场景模拟：验收时发现和开发理解不一致

> 开发完成了，你打开系统验收。点了一下"审批通过"，工单状态确实变了。你心想"没问题"，准备签字验收。
>
> 结果客服主管试用后说："为什么工单审批完了还在列表里？我上次审到哪了都搞不清，越审越乱。"
>
> 你回去翻 PRD，发现你只写了"工单状态更新为已通过"，没写"工单从列表中消失"或"标记为已读"。开发确实按 PRD 做了——只是你的 PRD 没写完整。

**问题出在哪？**

验收标准不够具体。你的 GWT 的 Then 部分只描述了数据库状态的变化，没有描述**用户在界面上看到什么**。

**正确的验收标准应该同时覆盖两个层面：**

| 层面 | 要回答的问题 | 示例 |
|------|-------------|------|
| 系统层 | 数据发生了什么变化？ | 工单状态从"待审批"变为"已通过" |
| 用户层 | 用户看到什么变化？ | 工单列表刷新，#1001 不再显示；右上角弹出"审批成功"提示 |

---

### 3.4 非功能性需求

功能性需求回答"系统做什么"，非功能性需求回答"系统做得怎么样"。

| 维度 | 含义 | 示例 |
|------|------|------|
| 性能 | 响应有多快 | 工单列表加载 ≤ 2 秒 |
| 并发 | 多少人同时用 | 支持 200 客服同时在线 |
| 安全 | 谁可以做什么 | 客服只能看自己分配的工单 |
| 可用性 | 系统有多可靠 | 月故障 ≤ 3.6 小时 |

## 四、从需求到 PRD：五步法

拿到模糊需求后，按以下顺序思考：

### 第 1 步：定位用户与场景（Who-When-Where-What）

- **谁**会用？（具体角色，不是"所有人"）
- **什么情况下**会用到？
- **在什么环境**下用？
- **想达成什么**？（用户的目标，不是功能）

### 第 2 步：画用户旅程

先列主流程（从头到尾的完整步骤），再挖异常分支：
- 权限不够？
- 数据被人改过？
- 网络断了？
- 操作一半想取消？
- 多人同时操作？

### 第 3 步：写 GWT

把用户旅程的每一步翻译成 GWT。正常路径 1 组，每个异常分支 1 组。

### 第 4 步：排优先级

- Must：没了这个，用户目标达不到
- Should：有更好，没它也能绕过去
- Won't：本期明确不做

### 第 5 步：填入模板

打开 [PRD 填空模板](./PRD填空模板.md)，把前 4 步的成果填入 7 个部分。

## 五、完整案例：AI 客服退货审批

> 这个案例演示五步法从头到尾的实际操作。你可以对照 [PRD 填空模板](./PRD填空模板.md) 中的示例区块，看每一步是如何映射到模板里的。

### 第 1 步：定位用户与场景

| 问题 | 答案 |
|------|------|
| 谁会用？ | 电商售后客服 |
| 什么情况下用？ | 退换货高峰期，日均处理上百单 |
| 在什么环境？ | PC 端后台系统 |
| 想达成什么？ | 标准退货快速审批，不再人工逐单审核 |

### 第 2 步：画用户旅程

**正常路径：** 客服打开工单列表 → 筛选"待审批" → 点击工单 → 确认退货类型 → 点击"审批通过" → 生成退货单号 → 工单从列表消失

**异常分支：**
1. 工单已被其他客服审批了
2. 退货类型是"异常退货"，不符合自动审批条件
3. 提交审批时网络中断
4. 客服没有该工单的审批权限

### 第 3 步：写 GWT

```
场景 1（正常审批）：
Given：工单 #1001 状态为"待审批"，属于标准退货类型
When：客服点击"审批通过"按钮
Then：工单状态更新为"已通过"；系统自动生成退货单号 RT+日期+序号；工单列表刷新，#1001 不再显示

场景 2（异常：已被他人审批）：
Given：工单 #1001 状态为"已通过"
When：客服点击"审批通过"按钮
Then：页面提示"该工单已被处理，请刷新列表"；工单列表自动刷新；不重复生成退货单号

场景 3（异常：退货类型不符）：
Given：工单 #1001 状态为"待审批"，属于"异常退货"类型
When：客服打开工单并尝试审批
Then：审批按钮置灰不可点击；显示提示"异常退货需人工处理，请联系主管"

场景 4（异常：网络中断）：
Given：工单 #1001 状态为"待审批"，当前网络不稳定
When：客服点击"审批通过"按钮
Then：页面提示"网络异常，请重试"；审批按钮恢复可点击；工单状态保持"待审批"不变
```

### 第 4 步：排优先级

| 类型 | 内容 |
|------|------|
| ✅ Must Have | 标准退货审批 / 冲突检测 / 类型校验 |
| 🔲 Should Have | 批量审批（一次审批多条） |
| ❌ Won't Have | 物流系统对接（下期）/ 客服绩效看板（另立项） |

### 第 5 步：填入模板

把以上内容填入 [PRD 填空模板](./PRD填空模板.md) 的对应位置，补充非功能性需求和风险假设，过自查清单 → 提交评审。

## 六、常见陷阱速查

| # | 陷阱 | 正确做法 |
|---|------|----------|
| 1 | 只写正常场景，不写异常场景 | 强制每个功能 ≥ 3 个异常场景 |
| 2 | GWT 写得太模糊 | 用"QA 能据此写出测试用例吗？"检验 |
| 3 | Must Have 列太多 | Must = 不做就失败，通常 ≤ 5 项 |
| 4 | 不敢写 Won't Have | 敢说不做，才意味着想清楚了做什么 |
| 5 | 用模糊词汇（"优化""改善"） | 替换为可量化指标 |
| 6 | 目标用户写成"所有用户" | 必须是具体角色 |
| 7 | 验收标准只描述数据库变化 | 同时描述用户在界面上看到什么 |
| 8 | PRD 写完就以为完事了 | 定稿后对接 API Fox 生成 Mock |

## 七、下一步

1. 打开 [PRD 填空模板](./PRD填空模板.md)，把模板复制一份开始填写
2. 填写完成后，对照文末的**自查清单**逐项打勾
3. 提交评审（产品负责人主持 + 至少 1 名工程师参与）
4. 评审通过后，在 API Fox 中将第 4 节 GWT 映射为 API Mock，前后端并行开发

> PRD 不是写出来的，是**评出来的**。那些在评审中把你问住的问题，才是这份文档真正完善的地方。
