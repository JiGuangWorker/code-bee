# 代码实现

> 在编码规范约束下，写能解决眼前问题的最少代码。极简、精准、不动不该动的。

---

## 角色行为

你写代码的目标不是"全面"，不是"灵活"，是**刚好解决当前 Issue 的要求，不多一行**。

Karpathy 的测试标准："如果某样东西被抽象出来的唯一理由是'以防万一'，那你就过度构建了。" 判断标准："你能为每一行改动找到和用户需求的直接关联吗？找不到，就撤回。"

核心规则：
- 写完一行，问自己：这行跟 Issue 直接相关吗？无关就删
- 照搬已有模式，不发明新风格
- 加依赖前先问标准库能不能搞定

> **本技能的 AI 定位：** AI 在编码规范约束下生成代码，遵循已有模式，最小化 diff。人逐行确认代码正确性后提交。

## 编码纪律

### 纪律 1：极简主义

写能解决眼前问题的最少代码，不是能解决所有未来版本的最少代码。

| ✅ 正确 | ❌ 错误 |
|---------|---------|
| 当前只需要一种支付方式，直接实现 | "以后可能接微信/支付宝/银联，先抽象个 PaymentGateway 接口" |
| 当前只有 3 个状态，用 if/switch | "以后状态会变多，先上状态机模式" |
| 当前只有一个调用方，内联逻辑 | "以后可能复用，提取成公共函数" |

**判断标准：** 删掉"以防万一"的代码后，功能还能完整跑通吗？能 → 那些代码就是多余的。

### 纪律 2：精准手术

diff 应该和任务一样小。不碰没让改的，不改格式。

| 操作 | 规则 |
|------|------|
| 修改已有代码 | 只改跟 Issue 直接相关的行 |
| 新增代码 | 放在已有模式指定的位置，不另起炉灶 |
| 格式化 | 不动。哪怕缩进不完美，除非 Issue 明确要求修格式 |
| 重构 | 不在本次改动范围内。另起 Issue |
| import | 只加用到的，删掉用不到的。不顺手"整理" |

**核心原则：** 格式化器跑一遍会把真正重要的三行改动埋在三百行无关变更里。Review 的人找不到重点，你就失败了。

### 纪律 3：依赖即负债

每一个依赖都是你无法控制的永久代码。

**添加依赖的决策流程：**

```
需要某个功能
    │
    ├─ 标准库能不能搞定？──→ 能 → 用标准库，不加依赖
    │
    ├─ 已有依赖能不能搞定？──→ 能 → 用已有依赖，不加新的
    │
    └─ 必须加新依赖 → 回答三个问题：
         1. 为什么标准库和已有依赖搞不定？
         2. 这个依赖维护活跃吗？有安全风险吗？
         3. 有没有更轻量的替代？
```

| 场景 | ❌ 错误 | ✅ 正确 |
|------|---------|---------|
| 生成 UUID | npm install uuid | `crypto.randomUUID()` |
| HTTP 请求 | 引入 axios（项目已用 fetch） | 照搬项目已有的 fetch 封装 |
| 日期格式化 | 引入 moment.js（260KB） | `Intl.DateTimeFormat` 或项目已用的轻量库 |

### 纪律 4：说清楚

代码提交时，PR 描述不是说"修复了 XX 问题"就完事。

**PR 描述必须包含：**

| 内容 | 说明 |
|------|------|
| 做了什么 | 改了哪些文件、每个文件改了什么 |
| 为什么这么做 | 技术决策的理由（为什么选 A 不选 B） |
| 不确定的事 | 精确描述，如"我不确定这个库是否支持流式传输" |
| 没做什么 | 相关但不在此次范围内的，明确排除 |

**好的沟通 vs 坏的沟通：**

| ❌ 坏的 | ✅ 好的 |
|--------|--------|
| "我觉得这应该能用" | "我在本地用 3 组数据测过，都通过。但并发场景没测，不确定加锁策略是否够" |
| 丢一块代码，没有说明 | "改了三处：① handler 加了参数校验 ② service 补了异常路径 ③ 数据库加了唯一索引防重" |

## 翻车信号识别

写代码过程中，一旦发现自己处于以下状态 → **立刻停手，重新评估**：

| 翻车模式 | 信号 | 正确动作 |
|----------|------|----------|
| **Kitchen Sink**（修水龙头拆了整个厨房） | 改着改着发现动了 5+ 个不相干的文件 | 回退，只保留跟 Issue 直接相关的改动 |
| **Wrong Abstraction**（该抽象的不抽象） | 同一段逻辑复制粘贴了 3 遍还在复制 | 第 3 次出现时提取函数/方法 |
| **Over Abstraction**（不该抽象的瞎抽象） | 写了个接口只为"以后好扩展" | 删掉接口，直接写具体实现 |
| **Optimistic Path**（盲目乐观） | 代码只处理了正常流程，异常路径全空着 | 逐条对着 [任务理解](任务理解.md) 的异常清单补齐 |
| **Runaway Refactor**（失控连锁） | 改 A 发现要改 B，改 B 发现要改 C…… | 停手。B、C 不在本次 Issue 范围 → 记下来，另起 Issue |

## 检查清单

提交代码前逐项确认：

| # | 检查项 | 对应纪律 |
|---|--------|----------|
| 1 | 每行改动都能说出跟 Issue 的关联？ | 极简主义 |
| 2 | 有没有"以防万一"的代码可以删？ | 极简主义 |
| 3 | diff 里有没有跟 Issue 无关的文件？ | 精准手术 |
| 4 | diff 里有没有纯格式变更？ | 精准手术 |
| 5 | 有没有新增依赖？加了的话理由写了吗？ | 依赖即负债 |
| 6 | 新增依赖前确认标准库/已有依赖搞不定了吗？ | 依赖即负债 |
| 7 | PR 描述说清楚了做了什么、为什么、不确定什么？ | 说清楚 |
| 8 | 有没有触发五种翻车模式？ | 翻车识别 |

> 8 项全部满足 → 进入 [自测验证](自测验证.md)。任一项不满足 → 修正后再提交。
