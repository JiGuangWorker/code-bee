# 可观测性规范

> **适用角色：** 所有工程师（前端 + 后端）
> **对标原则：** 《第一条 交付诚信原则》——系统运行状态必须可验证
> **版本：** v1.0

---

## 一、定位

可观测性不是"出了问题才查日志"，而是**系统在运行中持续暴露内部状态的能力**。

线上问题从"用户反馈才知道"变成"系统主动告警"，依赖三个支柱：

```
日志（Logging）  →  发生了什么
指标（Metrics）  →  系统表现如何
追踪（Tracing）  →  请求经过了哪些节点
```

**前后端必须统一实现这三者，缺一不可。**

---

## 二、统一标识：Trace ID

> 所有请求在入口处生成一个 `trace_id`，贯穿整个调用链路。用户反馈问题时，只需提供 trace_id，即可定位完整调用链。

### 2.1 生成规则

| 规则 | 说明 |
|------|------|
| 格式 | 32 位十六进制字符串（类似 UUID 去掉 `-`） |
| 生成位置 | 后端：HTTP 请求中间件；前端：页面加载时生成 session 级 ID |
| 注入方式 | 后端写入 `context.Context`；前端挂载到全局 logger 实例 |
| 传递方式 | 请求 Header `X-Trace-Id`；响应 Header 原样带回 |

### 2.2 后端实现

```go
// middleware/trace.go — 每个请求入口生成 trace_id
func TraceMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        traceID := c.GetHeader("X-Trace-Id")
        if traceID == "" {
            traceID = generateTraceID()
        }
        c.Header("X-Trace-Id", traceID)
        ctx := context.WithValue(c.Request.Context(), "trace_id", traceID)
        c.Request = c.Request.WithContext(ctx)
        c.Next()
    }
}
```

### 2.3 前端实现

```ts
// shared/utils/trace.ts
const sessionTraceId = crypto.randomUUID().replace(/-/g, '');

// 所有请求自动带上 trace_id
request.interceptors.request.use((config) => {
  config.headers['X-Trace-Id'] = sessionTraceId;
  return config;
});
```

| 规则 | 说明 |
|------|------|
| ❗ 每个请求必须有 trace_id | 中间件空值自动生成，不依赖调用方传入 |
| ❗ trace_id 必须写入日志 | 每条日志都带 trace_id 字段 |
| ❗ 错误提示必须露出 trace_id | 用户看到"系统异常，请反馈 trace_id: xxx" |
| ❗ 跨服务调用必须透传 | 调用下游服务时 Header 带 `X-Trace-Id` |

## 三、后端可观测性（Go）

### 3.1 日志

#### 格式

```json
{
  "timestamp": "2026-06-27T10:30:00.000Z",
  "level": "INFO",
  "trace_id": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
  "span_id": "op1",
  "caller": "service/user_service.go:42",
  "message": "user created",
  "user_id": "12345",
  "duration_ms": 120
}
```

#### 要求

| 规则 | 说明 |
|------|------|
| ❗ 生产环境日志格式为 JSON | 结构化日志，便于日志平台检索和聚合 |
| ❗ 每条日志必须带 `trace_id` | 通过 context 提取，不能漏 |
| ❗ 禁止 `fmt.Println` / `log.Println` | 统一用结构化 logger（如 zap） |
| ❗ 禁止在日志中打印敏感信息 | 密码、token、身份证号、手机号——脱敏或禁止 |
| ❗ 生产环境日志级别 ≥ INFO | 禁止 DEBUG 日志进生产 |

#### 日志级别使用

| 级别 | 含义 | 使用场景 |
|------|------|----------|
| DEBUG | 开发调试信息 | 本地开发，不进生产 |
| INFO | 关键业务节点 | 订单创建、用户注册、状态变更 |
| WARN | 非预期但可恢复 | 重试、降级、缓存穿透 |
| ERROR | 需要人工介入 | 数据库连接失败、第三方接口不可用 |

```go
// ✅ 正确：结构化日志，带 trace_id
logger.Info("order created",
    zap.String("order_id", order.ID),
    zap.Int64("amount", order.Amount),
)

// ✅ 正确：ERROR 级别记录完整堆栈
logger.Error("failed to create order",
    zap.Error(err),
    zap.String("user_id", req.UserID),
)

// ❌ 错误：纯文本日志
fmt.Printf("order %s created\n", order.ID)

// ❌ 错误：打印敏感信息
logger.Info("user login", zap.String("password", req.Password))
```

### 3.2 指标（Metrics）

#### 必须暴露的指标（RED 方法论）

| 指标 | 类型 | 含义 | 标签 |
|------|------|------|------|
| `http_requests_total` | Counter | 请求总数 | method, endpoint, status |
| `http_request_duration_seconds` | Histogram | 请求延迟 | method, endpoint |
| `http_requests_errors_total` | Counter | 错误请求数 | method, endpoint, status |

#### 暴露方式

```
GET /metrics  →  Prometheus 格式
```

```go
// ✅ 中间件自动采集，业务代码无需手动埋点
router.Use(prometheusMiddleware())

// 自定义业务指标示例
orderCreatedCounter := promauto.NewCounter(prometheus.CounterOpts{
    Name: "orders_created_total",
    Help: "Total number of orders created",
})
```

| 规则 | 说明 |
|------|------|
| ❗ `/metrics` 端点必须实现 | 没有例外 |
| ❗ HTTP 指标由中间件自动采集 | 业务代码不重复写 |
| ❗ 业务指标在 service 层埋点 | 不在 handler 层埋 |
| ❗ 延迟用 Histogram 不用 Summary | Histogram 可聚合，Summary 不可 |

### 3.3 链路追踪（Tracing）

#### Span 定义

| 概念 | 说明 |
|------|------|
| Trace | 一次完整的请求链路，由 trace_id 标识 |
| Span | 链路中的一个操作单元（如"查询数据库"、"调用第三方 API"） |
| Span Context | 跨进程传递 trace_id + span_id 的载体 |

#### 最小实现

```go
// ✅ 每个外部调用包裹一个 Span
func (s *Service) CreateOrder(ctx context.Context, req CreateOrderRequest) (*Order, error) {
    // 1. 查询用户
    user, err := s.queryUser(ctx, req.UserID)

    // 2. 扣减库存
    err = s.deductStock(ctx, req.ProductID, req.Quantity)

    // 3. 创建订单
    order, err := s.repo.Create(ctx, order)
    return order, nil
}

// 每个子操作独立 Span
func (s *Service) queryUser(ctx context.Context, userID string) (*User, error) {
    span, ctx := tracer.Start(ctx, "queryUser")
    defer span.End()

    user, err := s.userRepo.FindByID(ctx, userID)
    if err != nil {
        span.RecordError(err)
        return nil, err
    }
    span.SetAttributes(attribute.String("user_id", userID))
    return user, nil
}
```

| 规则 | 说明 |
|------|------|
| ❗ 每个跨进程调用必须创建 Span | DB 查询、RPC 调用、HTTP 请求 |
| ❗ Span 必须记录错误 | `span.RecordError(err)` |
| ❗ Span 名称为操作名 | 如 `queryUser`、`deductStock`，不要用 URL |
| ❗ 不追踪 Span 的内部细节 | 只关心"调了什么、花了多久、成功还是失败" |

#### 工具推荐

| 层 | 推荐工具 | 说明 |
|----|----------|------|
| 日志 | zap | Go 生态标准结构化日志库 |
| 指标 | prometheus/client_golang | Prometheus 官方 SDK |
| 追踪 | OpenTelemetry Go SDK | 厂商中立，可对接 Jaeger/Zipkin/云厂商 |

## 四、前端可观测性（TypeScript / React）

### 4.1 日志

| 规则 | 说明 |
|------|------|
| ❗ 禁止 `console.log` 进生产 | 构建时 strip 掉，或替换为 noop |
| ❗ 用分级 console | `console.warn` / `console.error` 保留，`console.log` 禁止 |
| ❗ 错误必须上报 | 全局 `window.onerror` + `unhandledrejection` 捕获后上报 |
| ❗ 上报附带 trace_id | 从请求 Header 中提取 |

```ts
// ✅ 全局错误捕获
window.addEventListener('error', (event) => {
  reportError({
    message: event.message,
    stack: event.error?.stack,
    trace_id: getCurrentTraceId(),
    url: window.location.href,
    timestamp: Date.now(),
  });
});

window.addEventListener('unhandledrejection', (event) => {
  reportError({
    message: event.reason?.message || 'Unhandled Promise Rejection',
    stack: event.reason?.stack,
    trace_id: getCurrentTraceId(),
  });
});
```

### 4.2 性能指标

> 前端必须采集 Web Vitals，不依赖后端。

| 指标 | 含义 | 采集方式 | 阈值 |
|------|------|----------|------|
| LCP | 最大内容绘制 | `web-vitals` 库 | < 2.5s |
| FID | 首次输入延迟 | `web-vitals` 库 | < 100ms |
| CLS | 累计布局偏移 | `web-vitals` 库 | < 0.1 |
| FCP | 首次内容绘制 | `web-vitals` 库 | < 1.8s |

```ts
import { onLCP, onFID, onCLS, onFCP } from 'web-vitals';

onLCP((metric) => reportMetric({ name: 'LCP', value: metric.value, trace_id: getCurrentTraceId() }));
onFID((metric) => reportMetric({ name: 'FID', value: metric.value, trace_id: getCurrentTraceId() }));
onCLS((metric) => reportMetric({ name: 'CLS', value: metric.value, trace_id: getCurrentTraceId() }));
onFCP((metric) => reportMetric({ name: 'FCP', value: metric.value, trace_id: getCurrentTraceId() }));
```

### 4.3 请求监控

> 所有 HTTP 请求通过拦截器自动采集，业务代码无需手动埋点。

```ts
// request.ts — 拦截器自动采集
request.interceptors.request.use((config) => {
  config.metadata = { startTime: Date.now() };
  return config;
});

request.interceptors.response.use(
  (response) => {
    const duration = Date.now() - response.config.metadata.startTime;
    reportMetric({
      name: 'api_request_duration',
      value: duration,
      tags: { endpoint: response.config.url, status: response.status },
    });
    return response;
  },
  (error) => {
    reportError({
      message: error.message,
      endpoint: error.config?.url,
      status: error.response?.status,
      trace_id: getCurrentTraceId(),
    });
    return Promise.reject(error);
  }
);
```

| 规则 | 说明 |
|------|------|
| ❗ 请求监控由拦截器统一处理 | 不分散到各组件 |
| ❗ 错误上报不阻塞页面 | 用 `navigator.sendBeacon` 或异步上报 |
| ❗ 不上报敏感信息 | 请求 body 中的密码、token 等脱敏后上报 |

## 五、告警规则

> 可观测的最终目的是"在用户之前发现问题"。以下为必须配置的告警：

| 告警 | 条件 | 级别 |
|------|------|------|
| 错误率飙升 | 5xx 比例 > 5%（持续 5 分钟） | P1 |
| 延迟升高 | P95 延迟 > 2s（持续 5 分钟） | P2 |
| 可用性下降 | 服务健康检查连续 3 次失败 | P0 |
| 前端 JS 错误激增 | 5 分钟内错误数 > 100 | P2 |
| 磁盘/内存 | 使用率 > 85% | P2 |
