# 编码规范

> **适用角色：** 所有工程师
> **适用语言：** Go、TypeScript/React
> **版本：** v1.0

---

## 一、通用原则

| 原则 | 说明 |
|------|------|
| **可读性优先** | 代码是写给人看的，AI 生成后必须人工扫一遍 |
| **一个函数只做一件事** | 超过 80 行必须拆分 |
| **不写魔法数字** | 用命名常量替代，AI 最容易产生这个问题 |
| **显式优于隐式** | 不要炫技，写最直白的写法 |
| **错误必须处理** | 不允许 `_` 吞掉 error（Go），不允许空 catch（TS） |

## 二、Go 编码规范

### 2.1 命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 包名 | 全小写、单数、简短 | `handler`、`service`、`model` |
| 文件名 | 全小写、下划线分隔 | `user_service.go`、`handler_profile.go` |
| 接口 | 单方法接口用 `-er` 后缀，多方法用名词 | `Reader`、`UserRepository` |
| 结构体 | 大驼峰 | `UserService`、`CreateOrderRequest` |
| 变量 | 小驼峰，缩写全大写 | `userID`、`httpClient` |
| 常量 | 大驼峰（导出）或小驼峰（私有） | `MaxRetryCount`、`defaultTimeout` |
| 测试函数 | `Test<函数名>_<场景>_<期望>` | `TestCreateUser_InvalidEmail_ReturnsError` |

### 2.2 错误处理

```go
// ✅ 正确：显式处理，包裹上下文
func GetUser(id string) (*User, error) {
    user, err := repo.FindByID(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("GetUser: find user %s: %w", id, err)
    }
    return user, nil
}

// ❌ 错误：吞掉 error
user, _ := repo.FindByID(ctx, id)

// ❌ 错误：只返回原始 error，丢失上下文
return repo.FindByID(ctx, id)
```

**规则：**

| 规则 | 说明 |
|------|------|
| ❗ 不允许 `_` 忽略 error | 除非有注释说明理由 |
| ❗ 向上传递必须用 `%w` 包裹 | 保留错误链，上层可 `errors.Is` 判断 |
| ❗ 禁止 `panic` 处理业务错误 | panic 只用于不可恢复的初始化失败 |
| ❗ 自定义错误类型放 `pkg/errcode/` | 统一错误码 + 统一响应格式 |

import (

### 2.4 接口定义

> **依赖倒置原则（Dependency Inversion Principle）**：高层模块不应依赖低层模块，二者都应依赖抽象。
> 在 Go 中的实践——**调用方定义接口，实现方实现接口**。这也是从根源防止循环引用的唯一方式。

```go
// ✅ 正确：调用方（service）定义自己需要的接口
// 文件：internal/module/user/service/service.go
type Repository interface {
    FindByID(ctx context.Context, id string) (*model.User, error)
    Create(ctx context.Context, user *model.User) error
}

type Service struct {
    repo Repository   // 依赖的是接口，不是具体实现
}

// ✅ 正确：实现方（repository）只管实现，不定义接口
// 文件：internal/module/user/repository/mysql.go
type MySQLRepo struct { db *sql.DB }
func (r *MySQLRepo) FindByID(ctx context.Context, id string) (*model.User, error) { ... }
func (r *MySQLRepo) Create(ctx context.Context, user *model.User) error { ... }

// 依赖方向（单向）：
//   service ──定义──▶ Repository interface
//   service ──依赖──▶ Repository interface ◀──实现── repository
//   repository 不 import service → 永无循环引用

// ❌ 错误：实现方定义接口 → 双向依赖
// 文件：internal/module/user/repository/repository.go
// type Repository interface { ... }      // 实现方定义了接口
// 后果：如果 repository 需回调 service → import service → 形成环 → 编译失败
```

| 规则 | 说明 |
|------|------|
| ❗ 接口必须由调用方定义 | 谁用谁定义，实现方不定义接口 |
| ❗ 实现方不 import 调用方 | repository/ 包内禁止 import service/ 包 |
| ❗ 接口小而精 | 单方法接口优先，多方法接口不超过 5 个方法 |
| ❗ 不返回具体类型 | 返回 interface，接收具体类型 |
| ❗ 此模式从根源杜绝循环引用 | Go 编译器禁止包级循环 import，调用方定义接口保证依赖单项 |

### 2.5 Context

> 任何涉及 I/O、网络调用或可能被外部中断的长时间操作，**必须** 接收 `context.Context` 作为第一个参数。

```go
// ✅ 正确：context 永远是第一个参数，逐层传递
func (s *Service) CreateUser(ctx context.Context, req CreateUserRequest) (*User, error) {
    // 传给下层
    return s.repo.Create(ctx, user)
}

// ✅ 正确：在调用链起点设置超时/取消
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
user, err := svc.CreateUser(ctx, req)

// ❌ 错误：context 不在第一位
func (s *Service) CreateUser(req CreateUserRequest, ctx context.Context) (*User, error)

// ❌ 错误：涉及 DB 查询却不接收 context
func (r *UserRepo) FindAll() ([]User, error)   // 外部无法中断

// ❌ 错误：把 context 存到 struct 里
// type Service struct { ctx context.Context }  // 禁止
```

| 规则 | 说明 |
|------|------|
| ❗ context 必须是第一个参数 | 无例外 |
| ❗ 涉及 I/O、网络、DB、长时间运算的方法必须接收 context | 确保外部可主动中断（超时/取消/优雅退出） |
| ❗ 不确定是否需要时，加 | 宁可多传不可少传，后续去掉比补上容易 |
| ❗ 逐层传递，不存储 | 不要把 ctx 存到 struct 字段，每次调用时传递 |
| ❗ 调用链起点设置超时 | `context.WithTimeout` / `WithCancel` 在最外层触发 |

### 2.6 Panic 兜底

> Go 后端所有代码必须实现三层 panic 兜底，任何一层遗漏都视为不合规。
> panic 不是错误处理手段，必须通过 recover 拦截，记录现场后优雅恢复。

#### 三层兜底机制

```
第一层：HTTP 中间件  →  每个请求一个 recover 边界
第二层：goroutine    →  每个 goroutine 必须有 defer+recover
第三层：进程入口     →  main 函数最外层 defer+recover 保底
```

#### 第一层：HTTP Recovery 中间件

```go
// ✅ 正确：每个 HTTP 请求必须被 recovery 中间件包裹
router := gin.New()
router.Use(gin.Recovery())  // gin 内置 recovery，但需覆盖日志格式

// ✅ 推荐：自定义 recovery 中间件，写入结构化日志 + trace_id
func RecoveryMiddleware(logger *zap.Logger) gin.HandlerFunc {
    return func(c *gin.Context) {
        defer func() {
            if r := recover(); r != nil {
                traceID := c.GetString("trace_id")
                logger.Error("http handler panic recovered",
                    zap.String("trace_id", traceID),
                    zap.String("method", c.Request.Method),
                    zap.String("path", c.Request.URL.Path),
                    zap.Any("panic", r),
                    zap.Stack("stack"),
                )
                metrics.PanicRecoveries.WithLabelValues("http").Inc()
                c.AbortWithStatusJSON(500, gin.H{
                    "code":     10006,
                    "msg":      "系统繁忙，请稍后重试",
                    "trace_id": traceID,
                    "data":     nil,
                })
            }
        }()
        c.Next()
    }
}
```

#### 第二层：Goroutine Recovery

```go
// ✅ 正确：每个 goroutine 必须 defer+recover
// 工具函数：safe goroutine 启动器
func SafeGo(fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                logger.Error("goroutine panic recovered",
                    zap.Any("panic", r),
                    zap.Stack("stack"),
                )
                metrics.PanicRecoveries.WithLabelValues("goroutine").Inc()
            }
        }()
        fn()
    }()
}

// ✅ 正确：使用 SafeGo 启动所有 goroutine
SafeGo(func() {
    processBatch(ctx, items)
})

// ❌ 禁止：裸 go 关键字
// go processBatch(ctx, items)
```

| 规则 | 说明 |
|------|------|
| ❗ 禁止裸 `go` 关键字 | 必须通过 `SafeGo` 或等价封装启动 goroutine |
| ❗ goroutine 内 panic 不崩进程 | recover 后记录 FULL stack，不影响其他请求 |
| ❗ recover 必须记录堆栈 | `debug.Stack()` 或 zap.Stack()，不记录堆栈的 recover 无效 |
| ❗ recover 后必须记 metrics | `panic_recoveries_total{layer="goroutine"}` 计数器 +1 |
| ❗ 有 trace_id 时必须带入日志 | 如 goroutine 在请求上下文内启动，传入 ctx 提取 trace_id |

#### 第三层：进程入口 Recovery

```go
// ✅ 正确：main 函数最外层 defer+recover 保底
func main() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("FATAL: process panic: %v\n%s", r, debug.Stack())
            // 尝试 flush 日志缓冲区
            logger.Sync()
            os.Exit(1)
        }
    }()

    app, err := bootstrap.New()
    if err != nil {
        log.Fatalf("bootstrap failed: %v", err)
    }
    app.Run()
}
```

| 规则 | 说明 |
|------|------|
| ❗ main 必须有 defer+recover | 兜底未被上层捕获的 panic |
| ❗ 退出前 flush 日志 | 确保 panic 前缓冲区日志不丢失 |
| ❗ 退出码为 1 | 容器编排平台据此判断进程异常退出 |

#### 禁止事项

> 以下编码模式视为不合规，Code Review 时必须检出。

| 禁止模式 | 原因 | 正确做法 |
|----------|------|----------|
| `go processBatch(ctx, items)` | 裸 goroutine 无 recover | 用 `SafeGo` 封装 |
| `recover()` 后什么都不做 | 吞掉 panic 无法排查 | 至少记日志 + 记指标 |
| 用 `panic` 处理业务错误 | panic 是程序 bug，不是错误处理 | 用 `error` 返回值 |
| HTTP handler 不加 recovery | 一个 handler panic 崩整个服务 | router 必须挂 recovery 中间件 |

### 2.7 并发

> goroutine 是 Go 的核心优势，但也是 bug 高发区。并发代码必须可读、可中断、可观测。

#### 2.7.1 goroutine 启动规范

> 所有 goroutine 必须通过 `SafeGo` 启动（详见 2.6 Panic 兜底），在此基础上还需满足生命周期可控。

```go
// ✅ 正确：context 驱动的 goroutine，可随时取消
func (s *Service) StartWorker(ctx context.Context) {
    SafeGo(func() {
        for {
            select {
            case <-ctx.Done():
                logger.Info("worker stopped")
                return
            case task := <-s.taskCh:
                s.process(ctx, task)
            }
        }
    })
}

// ❌ 禁止：无限循环无退出机制
func (s *Service) StartWorker() {
    SafeGo(func() {
        for {
            task := <-s.taskCh
            s.process(context.Background(), task)  // 永远无法停止
        }
    })
}
```

| 规则 | 说明 |
|------|------|
| ❗ goroutine 必须可退出 | 通过 context 取消或 channel close 信号 |
| ❗ 禁止无限循环无 select | `for {}` 或 `for range ch` 无退出路径 |
| ❗ goroutine 数量必须有上限 | 禁止根据请求动态创建无界 goroutine |

#### 2.7.2 并发编排：errgroup

> 需要并发执行多个子任务并等待全部完成时，使用 `errgroup` 而非手写 `sync.WaitGroup`。
> errgroup 的核心优势：任一子任务失败即取消其余、自动 error 聚合。

```go
import "golang.org/x/sync/errgroup"

// ✅ 正确：errgroup 并发编排，快速失败
func (s *Service) CreateOrder(ctx context.Context, req CreateOrderRequest) (*Order, error) {
    g, ctx := errgroup.WithContext(ctx)

    var user *User
    var product *Product

    g.Go(func() error {
        var err error
        user, err = s.userRepo.FindByID(ctx, req.UserID)
        return err
    })
    g.Go(func() error {
        var err error
        product, err = s.productRepo.FindByID(ctx, req.ProductID)
        return err
    })

    if err := g.Wait(); err != nil {
        return nil, fmt.Errorf("CreateOrder: %w", err)
    }

    // 两个查询都成功后，继续创建订单
    return s.repo.Create(ctx, &Order{User: user, Product: product})
}

// ❌ 禁止：裸 WaitGroup 手写错误收集
// var wg sync.WaitGroup
// var mu sync.Mutex
// var errs []error
// wg.Add(2)
// go func() { defer wg.Done(); ... }()
// ...样板代码多，容易遗漏 wg.Done()
```

| 规则 | 说明 |
|------|------|
| ❗ 多子任务并发用 `errgroup` | 不用 `sync.WaitGroup` |
| ❗ `errgroup.WithContext` 用派生 ctx | 子任务失败自动取消其余 |
| ❗ 限制并发度用 `SetLimit` | `g.SetLimit(10)` 防止 goroutine 爆炸 |
| ❗ 子任务闭包注意变量捕获 | 循环中用 `i := i` 或传参，避免闭包陷阱 |

#### 2.7.3 Worker Pool（有界并发）

> 处理批量任务时，必须限制并发 goroutine 数量，防止打爆下游。

```go
// ✅ 正确：有界 worker pool，并发度可控
func (s *Service) BatchProcess(ctx context.Context, items []Item) error {
    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(10)  // 最多 10 个 goroutine 并发

    for _, item := range items {
        item := item  // 闭包变量捕获
        g.Go(func() error {
            return s.processOne(ctx, item)
        })
    }

    return g.Wait()
}
```

| 规则 | 说明 |
|------|------|
| ❗ 批量处理必须设并发上限 | 通过 `SetLimit` 或 buffered channel 做信号量 |
| ❗ 上限值可配置 | 不硬编码，通过环境变量或配置文件设置 |
| ❗ 下游压力大时降低并发 | DB 连接数、第三方 API QPS 是上限的参考值 |

#### 2.7.4 共享数据安全

```go
// ✅ 正确：mutex 保护共享状态
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.value++
}

// ✅ 正确：sync.Map 适用于读多写少
var cache sync.Map

// ✅ 正确：channel 通信替代共享内存
// "不要通过共享内存来通信，而要通过通信来共享内存"

// ❌ 禁止：无保护的 map 并发读写
// m := make(map[string]int)
// go func() { m["a"] = 1 }()   // fatal error: concurrent map writes
// go func() { _ = m["a"] }()
```

| 规则 | 说明 |
|------|------|
| ❗ map 并发读写必须加锁或用 `sync.Map` | Go runtime 会 panic |
| ❗ `defer mu.Unlock()` 紧跟 `mu.Lock()` | 防止中间 return 漏解锁 |
| ❗ 优先用 channel 传递数据所有权 | 减少显式加锁的复杂度 |
| ❗ 用 `go test -race` 检测数据竞争 | CI 必须跑 race 检测 |

#### 2.7.5 禁止事项

| 禁止模式 | 原因 | 正确做法 |
|----------|------|----------|
| 无退出机制的 `for {}` goroutine | 优雅退出时卡死 | 加 `select + ctx.Done()` |
| 无并发上限的批量处理 | 打爆下游 | 用 `SetLimit` 或信号量 |
| 裸 `sync.WaitGroup` + 手写错误收集 | 样板代码多、易出错 | 用 `errgroup` |
| map 无锁并发读写 | runtime panic | 加锁或 `sync.Map` |
| goroutine 泄漏（channel 永远等不到） | 内存泄漏 | 确保有 `close` 或 context 取消 |

### 2.8 函数选项模式

> 任何对外提供服务的封装体（Service、Repository、库组件等），构造器/初始化函数 **必须** 使用函数选项模式。

```go
// 定义 Option 类型
type Option func(*Service)

// 每个可配置项一个 With* 函数
func WithTimeout(d time.Duration) Option {
    return func(s *Service) { s.timeout = d }
}
func WithLogger(logger *zap.Logger) Option {
    return func(s *Service) { s.logger = logger }
}

// 构造器接收可变 Option，内部设默认值
func NewService(opts ...Option) *Service {
    s := &Service{
        timeout: 30 * time.Second,   // 默认值
        logger:  zap.NewNop(),
    }
    for _, opt := range opts {
        opt(s)
    }
    return s
}

// ✅ 调用方按需组合，语义清晰
svc := NewService(
    WithTimeout(10 * time.Second),
    WithLogger(logger),
)

// ❌ 禁止：多参数构造器
func NewService(timeout time.Duration, logger *zap.Logger, db *sql.DB) *Service
```

| 规则 | 说明 |
|------|------|
| ❗ Option 类型名统一用 `Option` | 不要叫 `Config`、`ServiceOption` 等 |
| ❗ 每个可选项一个 `With*` 函数 | 返回值类型为 `Option`（闭包） |
| ❗ 构造器必须设默认值 | 零参数调用即可用，不依赖外部传参 |
| ❗ 禁止多参数构造器 | 超过 3 个参数的 New 函数必须重构为函数选项模式 |
| ❗ 新增配置项不加函数签名参数 | 只新增 `With*` 函数，不破坏已有调用方 |

### 2.9 幂等性

> 幂等性不是"锦上添花"，而是分布式系统的**基本要求**。
> 同一操作执行一次和执行多次，结果必须一致，副作用不叠加。

#### 2.9.1 需要幂等的场景

| 场景 | 示例 | 后果（无幂等） |
|------|------|---------------|
| 支付/扣款 | 用户双击支付按钮 | 重复扣款 |
| 订单创建 | 网络超时后用户重试 | 重复下单 |
| 库存扣减 | MQ 消息重复投递 | 超卖 |
| 积分发放 | 回调接口重试 | 多发积分 |
| 外部回调 | 第三方支付回调重复 | 重复处理 |

#### 2.9.2 方案一：数据库唯一约束（首选）

> 最可靠的幂等方案——依赖数据库的唯一索引保证。

```go
// ✅ 正确：通过唯一索引 + INSERT ON DUPLICATE 实现幂等
// 建表时创建唯一索引：UNIQUE KEY `uk_request_id` (`request_id`)

func (r *OrderRepo) Create(ctx context.Context, req CreateOrderRequest) (*Order, error) {
    order := &Order{
        RequestID: req.RequestID,  // 客户端生成的幂等键
        UserID:    req.UserID,
        Amount:    req.Amount,
        Status:    "created",
    }

    result := r.db.WithContext(ctx).Create(order)
    if result.Error != nil {
        // 判断是否是唯一键冲突
        if isDuplicateKeyError(result.Error) {
            // 查询已创建的订单返回
            var existing Order
            r.db.WithContext(ctx).
                Where("request_id = ?", req.RequestID).
                First(&existing)
            return &existing, nil
        }
        return nil, result.Error
    }
    return order, nil
}

func isDuplicateKeyError(err error) bool {
    // MySQL: Error 1062
    var mysqlErr *mysql.MySQLError
    return errors.As(err, &mysqlErr) && mysqlErr.Number == 1062
}
```

| 规则 | 说明 |
|------|------|
| ❗ 写操作入口必须有 request_id | 由客户端/上游生成，全程透传 |
| ❗ request_id 加唯一索引 | 数据库层面兜底，不依赖应用层逻辑 |
| ❗ 冲突时返回已有结果 | 不报错，正常返回首次执行的数据 |
| ❗ request_id 必须是请求级唯一 | 同一请求重试用相同 ID，新请求用新 ID |

#### 2.9.3 方案二：状态机（业务幂等）

> 通过业务状态流转确保同一操作不重复执行。

```go
// ✅ 正确：通过状态判断 + 数据库原子更新
func (s *Service) ApproveTicket(ctx context.Context, ticketID string) error {
    // UPDATE ... SET status = 'approved' WHERE id = ? AND status = 'pending'
    // RowsAffected = 0 → 已被处理（可能幂等返回，也可能状态冲突）

    result := s.db.WithContext(ctx).
        Model(&Ticket{}).
        Where("id = ? AND status = ?", ticketID, "pending").
        Updates(map[string]interface{}{
            "status":     "approved",
            "approved_at": time.Now(),
        })

    if result.RowsAffected == 0 {
        // 查询当前状态判断是幂等还是状态冲突
        var ticket Ticket
        s.db.First(&ticket, ticketID)
        switch ticket.Status {
        case "approved":
            return nil  // ✅ 幂等：已经是目标状态
        case "rejected":
            return errcode.ErrConflict.WithMsg("工单已被驳回，无法审批")
        default:
            return errcode.ErrConflict.WithMsg("工单状态异常")
        }
    }
    return nil
}
```

| 规则 | 说明 |
|------|------|
| ❗ WHERE 条件带当前状态 | `WHERE status = 'pending'` 不是 `WHERE id = ?` |
| ❗ 检查 RowsAffected | 为 0 时区分"幂等重复"和"非法状态迁移" |
| ❗ 幂等 ≠ 忽略错误 | 状态冲突时必须明确返回错误提示 |

#### 2.9.4 方案三：分布式锁 + 唯一键（高并发补充）

> 唯一约束是兜底，分布式锁是前置拦截。高并发场景两者组合使用。

```go
// ✅ 正确：先抢锁，再写库，唯一约束兜底
func (s *Service) CreateOrder(ctx context.Context, req CreateOrderRequest) (*Order, error) {
    lockKey := fmt.Sprintf("order:create:%s", req.RequestID)

    // 1. 尝试获取分布式锁（Redis SETNX + TTL）
    locked, err := s.redis.SetNX(ctx, lockKey, "1", 30*time.Second).Result()
    if err != nil {
        return nil, fmt.Errorf("acquire lock: %w", err)
    }
    if !locked {
        // 锁已被持有 → 查询已有结果返回
        return s.repo.FindByRequestID(ctx, req.RequestID)
    }
    defer s.redis.Del(ctx, lockKey)

    // 2. 执行业务逻辑（唯一约束兜底）
    return s.repo.Create(ctx, req)
}
```

| 规则 | 说明 |
|------|------|
| ❗ 锁必须有 TTL | 防止持锁进程崩溃导致死锁 |
| ❗ 锁释放后唯一约束兜底 | 极端情况锁过期，数据库拒重复写入 |
| ❗ 获取锁失败返回已有结果 | 不返回错误，视为幂等重放 |

#### 2.9.5 幂等键生成规范

```go
// ✅ 正确：客户端生成 request_id，格式统一
// 前端/上游：UUID v4，每次请求生成新 ID
// 重试时携带同一 ID

// ✅ 后端校验 request_id 格式
func validateRequestID(id string) error {
    if id == "" {
        return errors.New("request_id is required")
    }
    if len(id) > 64 {
        return errors.New("request_id too long")
    }
    return nil
}
```

| 规则 | 说明 |
|------|------|
| ❗ request_id 由调用方生成 | 后端不生成，只校验和使用 |
| ❗ 格式为 UUID 或等价唯一字符串 | 确保全局唯一 |
| ❗ 长度 ≤ 64 | 适配数据库索引限制 |
| ❗ 禁止用时间戳作幂等键 | 并发下可能重复 |

#### 2.9.6 幂等性 vs 非幂等接口

| 接口类型 | 示例 | 幂等要求 |
|----------|------|----------|
| 查询类（GET） | 列表查询、详情查询 | 天然幂等 |
| 更新类（PUT） | 全量更新资源 | 天然幂等 |
| 删除类（DELETE） | 删除资源 | 天然幂等 |
| 创建类（POST） | 下单、支付、发券 | **必须实现幂等** |
| 动作类（POST） | 发送验证码 | 需限频，可考虑幂等 |

#### 2.9.7 禁止事项

| 禁止模式 | 原因 | 正确做法 |
|----------|------|----------|
| POST 创建接口无幂等键 | 网络重试导致重复创建 | 加 request_id + 唯一约束 |
| 仅靠前端防重（按钮 loading） | 用户可绕过 | 后端必须独立实现幂等 |
| 幂等键用时间戳 | 并发重复概率高 | 用 UUID |
| 冲突时返回错误 | 用户看到"系统错误" | 返回已有结果 |

## 三、TypeScript / React 编码规范

### 3.1 命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 组件文件 | 大驼峰 `.tsx` | `UserList.tsx` |
| 组件目录 | 大驼峰 | `UserList/` |
| Hook 文件 | `use` 前缀 + 大驼峰 | `useAuth.ts` |
| 工具/类型/API 文件 | 小驼峰 | `formatDate.ts`、`userApi.ts` |
| 变量/函数 | 小驼峰 | `userName`、`fetchUserList` |
| 类型/接口 | 大驼峰，接口不用 `I` 前缀 | `User`、`OrderDetail` |
| 常量 | 全大写下划线 | `MAX_PAGE_SIZE` |

### 3.2 组件写法

```tsx
// ✅ 函数组件 + TypeScript 类型
interface UserCardProps {
  user: User;
  onDelete?: (id: string) => void;
}

export const UserCard: React.FC<UserCardProps> = ({ user, onDelete }) => {
  const handleDelete = () => onDelete?.(user.id);

  return (
    <div className={styles.card}>
      <h3>{user.name}</h3>
      <button onClick={handleDelete}>删除</button>
    </div>
  );
};

// ❌ 禁止：class 组件
// ❌ 禁止：any 类型
// ❌ 禁止：export default（统一用命名导出）
```

| 规则 | 说明 |
|------|------|
| ❗ 只用函数组件 | 禁止 class 组件 |
| ❗ 禁止 `any` | 必须定义明确类型 |
| ❗ 统一命名导出 | `export const`，不用 `export default` |
| ❗ Props 用 interface | 定义在组件文件顶部或 `types.ts` |

### 3.3 Hook 写法

```tsx
// ✅ 标准 Hook 结构
export const useUserList = (pageSize: number) => {
  const [users, setUsers] = useState<User[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  const fetchUsers = useCallback(async (page: number) => {
    setLoading(true);
    try {
      const data = await userApi.getList({ page, pageSize });
      setUsers(data.items);
    } catch (e) {
      setError(e instanceof Error ? e.message : '加载失败');
    } finally {
      setLoading(false);
    }
  }, [pageSize]);

  return { users, loading, error, fetchUsers };
};
```

| 规则 | 说明 |
|------|------|
| ❗ 返回对象而非数组 | `return { data, loading }` 优于 `return [data, loading]` |
| ❗ 异步操作必须有 loading/error | 三个状态缺一不可 |
| ❗ `useCallback` 包裹回调 | 避免子组件无意义重渲染 |

### 3.4 状态管理

| 规则 | 说明 |
|------|------|
| ❗ 组件内状态用 `useState` | 不出组件的数据就地管理 |
| ❗ 跨组件状态用 Context 或 store | 需要多组件共享的提升到 store |
| ❗ 服务端数据优先用 React Query | 缓存、重取、乐观更新交给框架 |
| ❗ 不用 Redux | 用 Zustand 或 React Context |

### 3.5 API 调用

```tsx
// ✅ API 定义放入模块 api 目录
// packages/user/src/api/userApi.ts
import { request } from '@project/app/api/request';

export const userApi = {
  getList: (params: PaginationParams) =>
    request.get<PaginatedResponse<User>>('/api/users', { params }),

  create: (data: CreateUserRequest) =>
    request.post<User>('/api/users', data),
};
```

| 规则 | 说明 |
|------|------|
| ❗ API 函数集中到 `api/` 目录 | 不在组件里直接写 fetch/axios |
| ❗ 统一用 request 实例 | 拦截器、token、超时集中在 `request.ts` |
| ❗ 响应必须有类型 | 泛型参数明确返回类型 |

### 3.6 样式

| 规则 | 说明 |
|------|------|
| ❗ 用 CSS Modules | `style.module.css`，禁止全局样式污染 |
| ❗ 不用内联样式对象 | `style={{color: 'red'}}` 禁止 |
| ❗ 不引入 CSS-in-JS 库 | 不用 styled-components |

### 3.7 目录引用

```tsx
// ✅ workspace 内引用用包名
import { Button } from '@project/shared/components/Button';
import { useAuth } from '@project/shared/hooks/useAuth';

// ❌ 禁止：相对路径跨领域引用
import { Button } from '../../../shared/components/Button';
```

### 3.8 构造选项模式

> TypeScript 中等效模式：使用 options 对象 + 默认解构，替代多参数构造函数。

```ts
interface ServiceOptions {
  timeout?: number;
  retries?: number;
}

// ✅ 正确：options 对象 + 默认值
function createService(options: ServiceOptions = {}): Service {
  const { timeout = 30000, retries = 3 } = options;
  return new Service(timeout, retries);
}

createService({ timeout: 5000 });           // 按需传参
createService();                             // 零参数可用

// ❌ 禁止：多参数构造函数
function createService(timeout: number, retries: number, logger: Logger): Service
```

| 规则 | 说明 |
|------|------|
| ❗ 构造函数参数超过 2 个必须用 options 对象 | 避免调用方必须记住参数顺序 |
| ❗ options 字段全部设为可选 | 零参数调用即可用 |
| ❗ 默认值写在与解构同行的位置 | `const { timeout = 30000 } = options` |
| ❗ 新增配置项只扩展 interface | 不破坏已有调用方 |

## 四、AI 编程特别约束

> 这些是 AI 最容易犯的错，Code Review 时优先检查。

| AI 常见错误 | 正确做法 |
|-------------|----------|
| 吞掉 error（`_` 忽略） | 每个 error 必须处理或显式注释 |
| 魔法数字 | 全部替换为命名常量 |
| `any` 类型 | 定义明确类型 |
| 超长函数（>200 行） | 拆分成多个小函数 |
| import 了没用到的包 | 删除 |
| 循环里用 `+=` 拼字符串 | Go 用 `strings.Builder`，TS 用数组 join |
| 忘记处理边界条件 | 空数组、null、undefined 必须处理 |
| 注释写的比代码还多 | 代码自解释，只注释"为什么"不注释"是什么" |

## 五、文件规模治理

> AI 生成代码容易产生超长文件，过长的文件不利于人工审查和维护。本章规定文件行数上下限，并提供拆分与合并的决策路径。

### 5.1 行数上限

| 语言 | 文件类型 | 上限 | 超出处理 |
|------|----------|------|----------|
| Go | 任意 `.go` | **500 行** | 必须按职责拆分 |
| TypeScript | 组件 `.tsx` | **300 行** | 必须提取子组件 |
| TypeScript | Hook / 工具 `.ts` | **200 行** | 必须按功能域拆分 |

### 5.2 行数下限

| 语言 | 下限 | 说明 |
|------|------|------|
| Go | **50 行** | 低于此值且无清晰独立职责的文件，考虑合并 |
| TypeScript | **30 行** | 除非有明确的独立复用价值，否则合并 |

### 5.3 拆分策略

当文件超过上限时，按以下优先级执行拆分：

| 优先级 | 策略 | 适用场景 | 示例 |
|--------|------|----------|------|
| 1 | **按职责拆分** | 一个文件承担了多个独立职责 | `handler.go` → `handler_create.go` + `handler_list.go` |
| 2 | **提取类型定义** | 类型/接口定义过多 | 抽取 `types.go` / `types.ts` |
| 3 | **提取辅助函数** | 纯函数工具方法堆积 | 抽取 `validator.go`、`formatter.go` |
| 4 | **提取子组件** | 组件 render 部分过复杂 | 拆出 `<UserCard />`、`<UserFilter />` |

### 5.4 合并策略

当文件低于下限时，满足以下任一条件应合并：

| 条件 | 操作 |
|------|------|
| 多个文件均 < 30 行，且功能强相关 | 合并为一个文件 |
| 仅包含一个接口/类型的独立文件 | 合并到使用方所在文件 |
| 仅包含 1~2 个简单常量的文件 | 合并到相关模块文件 |
