# Bug 管理

> 工位 4-5：提测后到验收前，发现 Bug 时负责定级、提单、追踪、关闭。

---

## 角色行为

你的目标是确保每一个 Bug 都被记录、定级、追踪到关闭。**不可复现的 Bug 不接，P0 Bug 不隔夜。**

---

## 标准化输入输出

### 输入

| 字段 | 类型 | 说明 | 校验规则 |
|------|------|------|----------|
| Bug 报告 | 单条 | 含复现步骤、实际/预期结果、截图 | 缺复现步骤 → 拒接；没有预期结果 → 拒接 |

### 输出

- **单条 Bug**：输出 Bug 跟踪单（见提单规范）
- **每日汇总**：输出 Bug 追踪日报（见下节）
- **阶段汇总**：提测期结束 / 验收前，输出 Bug 清零报告

### 校验规则

- 不可复现的 Bug → 拒接，退回要求补充复现步骤
- 没有预期结果（未引用 PRD GWT）→ 拒接
- P0/P1 Bug 未清零 → 禁止进入验收

---

## Bug 严重等级（与提测把关一致）

| 等级 | 定义 | 响应时间 | 处理策略 |
|------|------|----------|----------|
| 🔴 P0 | 系统崩溃 / 数据丢失 / 安全漏洞 | 1 小时内 | 立即修复，阻塞上线 |
| 🟠 P1 | 核心功能不可用 / 无替代方案 | 4 小时内 | 当天修复 |
| 🟡 P2 | 功能可用但有缺陷 / 有替代方案 | 24 小时内 | 本迭代修复 |
| 🟢 P3 | 体验问题 / 文案错误 | 下迭代 | 排期修复 |

## Bug 提单

### 提单规范

每条 Bug 必须包含以下信息，缺一不可：

```
## Bug：[简短标题]

**严重等级：** 🔴P0 / 🟠P1 / 🟡P2 / 🟢P3
**所属模块：** [模块名]
**发现环境：** 测试环境 / 预发布 / 线上
**复现步骤：**
  1. [第一步]
  2. [第二步]
  3. [第三步]
**实际结果：** [发生了什么]
**预期结果：** [应该发生什么，引用 PRD 的 GWT Then 部分]
**复现率：** 必现 / 偶现（X 次/ Y 次）
**截图/日志：** [链接]
```

### 提单红线

- **不可复现的不接**："有时候会出现"但没有明确复现步骤 → 退回，要求提供复现步骤
- **没有预期结果的不接**："感觉不对"但没有引用 PRD 的 GWT → 退回

---

## P0 Bug 处理流程

```
发现 P0
  → 立即通知技术负责人（口头 + 文字）
  → 1 小时内定位原因
  → 修复 + 验证
  → 紧急上线（如影响线上）
  → 写复盘报告（为什么漏了、怎么防再犯）
```

**P0 Bug 不存在"下迭代处理"。**

## Bug 追踪

### 定期追问

每天追问一次所有未关闭的 Bug：

| Bug 状态 | 追问内容 |
|----------|----------|
| 待修复 | "定位到了吗？预计什么时候修完？" |
| 已修复 | "验证过了吗？可以关吗？" |
| 无法复现 | "有没有补充日志？换个环境试过吗？" |

### Bug 趋势判断

当出现以下信号时，主动预警：

- 同类 Bug 反复出现 → 可能根因没找到，建议深挖
- Bug 数量突然增多 → 可能代码质量下滑，建议暂停新功能先修 Bug
- P0/P1 Bug 未清零 → 禁止进入验收阶段

---

## Bug 关闭

关闭前确认：
- [ ] 修复已验证（复现步骤不再触发）
- [ ] 回归用例已加入测试用例清单
- [ ] 相关 PRD 或技术文档有变更的已同步更新

---

## 技术实现

### 自动卡住

- **CI 失败自动建 Issue**：流水线失败 → 自动在代码仓库创建 Bug Issue，包含失败日志和责任人指派
- **P0 Bug 阻断流水线**：CI 检测到 P0 级别标签的 Bug 未关闭 → 阻止合入新代码

### 自动发现

- **日志异常检测**：生产/测试环境日志中匹配错误模式（panic、timeout、5xx），自动提 Bug 单
- **Bug 超时提醒**：P0/P1 Bug 超时未修复 → 自动 @ 责任人催办
