### 1.2 模块内部结构

每个业务模块按**职责**拆分为 handler/service/repository/model 四个独立子目录，各自是独立的 Go package：

```
internal/module/user/
│
├── handler/                    # HTTP/gRPC 请求处理 (package handler)
│   ├── handler.go              #   路由注册入口
│   ├── profile.go              #   个人信息 handler
│   ├── auth.go                 #   认证 handler
│   ├── admin.go                #   管理员操作 handler
│   └── *_test.go
│
├── service/                    # 业务逻辑 (package service)
│   ├── service.go              #   业务入口
│   ├── profile.go              #   个人资料逻辑
│   ├── auth.go                 #   认证逻辑
│   └── *_test.go
│
├── repository/                 # 数据访问 (package repository)
│   ├── repository.go           #   数据访问接口定义
│   ├── mysql.go                #   MySQL 实现
│   ├── cache.go                #   Redis 缓存实现
│   └── *_test.go
│
├── model/                      # 数据模型 (package model)
│   ├── entity.go               #   数据库 Entity
│   ├── request.go              #   请求 DTO
│   ├── response.go             #   响应 DTO
│   └── *_test.go
│
└── wire.go                     # 依赖注入 (package user)
```

| 目录 | Go 包名 | 职责 | 扩展方式 |
|------|---------|------|----------|
| `handler/` | `handler` | 请求处理：参数校验、序列化、调用 service、响应封装 | 按接口或功能点拆文件（不限数量） |
| `service/` | `service` | 业务逻辑：流程编排、事务管理、调用 repository | 按功能点拆文件（不限数量） |
| `repository/` | `repository` | 数据访问：接口定义 + 各数据源实现（DB / Redis / 外部 API） | 接口单文件，实现按数据源拆 |
| `model/` | `model` | 数据结构：Entity / DTO / 请求响应体 | 按实体或功能拆文件 |
| `wire.go`（根目录） | `user` | 依赖注入配置 | 单文件 |

#### 设计理念

> **每个职责在自己的目录里写，不管写多少个都在自己的目录里。**
> 根目录（wire.go）只做总体控制——把 handler/service/repository 组装到一起。

| 约束 | 说明 |
|------|------|
| ❗ 每个文件 ≤ 500 行 | AI 编程可控范围，超过必须拆文件 |
| ❗ 四个子目录是固定结构 | handler/service/repository/model 四个目录必须存在 |
| ❗ 根目录只能有 wire.go | 不允许在模块根目录放业务 .go 文件 |
| ❗ package 名 = 目录名 | handler/ → `package handler`，service/ → `package service` |
| ❗ 模块间不直接调对方的 repository | user.handler 不能 import order.repository，必须走 compositor |

#### 依赖方向（模块内部）

```
handler/  →  service/  →  repository/
   ↓             ↓
(调用 service)  (调用 repository)

model/   ←  被所有层引用
wire.go  →  组装 handler + service + repository
```

#### 小型模块

小型模块结构不变，每个目录可能只有 1 个文件：

```
internal/module/payment/
├── handler/
│   └── handler.go
├── service/
│   └── service.go
├── repository/
│   └── repository.go
├── model/
│   └── entity.go
└── wire.go
```

---

### 1.3 模块拆分原则

| 原则 | 说明 |
|------|------|
| **高内聚** | 一个模块内部的文件，只处理本领域的事。用户模块不管订单逻辑。 |
| **低耦合** | 模块 A 需要模块 B 的数据时，不允许 A.repository 直接查 B 的表。必须通过 B.service 的对外接口获取。 |
| **可独立测试** | 一个模块的 service 层可以 Mock 掉 repository 后独立跑通测试。 |
| **可独立部署（远期）** | 目录结构预留拆微服务的可能性：模块内部依赖只通过接口，不直接引具体实现。 |

---

### 1.4 跨模块编排（Compositor）

当一个业务流程需要多个模块协作时（如"下单"涉及用户、商品、订单、支付），**不允许模块间相互调用**，而是在 `internal/compositor/` 中统一编排：

```go
// internal/compositor/checkout.go
type CheckoutCompositor struct {
    userService    user.Service       // 接口，非具体类型
    productService product.Service
    orderService   order.Service
    paymentService payment.Service
}

func (c *CheckoutCompositor) Checkout(ctx context.Context, req CheckoutRequest) (*Order, error) {
    // 1. 校验用户状态
    // 2. 锁定商品库存
    // 3. 创建订单
    // 4. 发起支付
    // 5. 扣减库存
}
```

> Compositor 是唯一允许跨模块调用的层级。它不持有自己的 repository，只编排其他模块的 service。

---

### 1.5 依赖方向

```
Handler  →  Service  →  Repository
   ↓            ↓
(调用模块自己的 service)

Compositor  →  各模块 Service（接口）
                    ↓
              各模块 Repository（接口）
```

**规则：**
- 外层依赖内层（Handler → Service → Repository），内层不知道外层
- 模块之间通过接口依赖，不直接 import 对方的 repository
- Compositor 只依赖各模块的 Service 接口

---

### 1.6 新增模块的步骤

```
1. 在 internal/module/ 下新建目录，如 refund/
2. 创建 model.go（定义数据结构）
3. 创建 repository.go（定义数据访问接口 + 实现）
4. 创建 service.go（实现业务逻辑）
5. 创建 handler.go（处理 HTTP 请求）
6. 在 internal/router/router.go 中注册路由
7. 如果涉及多模块，在 compositor 中编排
```

### 1.7 命名规则

| 类型 | 规则 | 示例 |
|------|------|------|
| 模块目录 | 全小写，单数 | `user/`、`order/`、`product/` |
| 文件名 | 全小写，下划线分隔 | `user_repository.go` |
| 包名 | 与目录名一致 | package `user` |
| 接口 | 大驼峰，名词或形容词+er | `UserService`、`Repository` |
| 结构体 | 大驼峰 | `UserRepository`、`CreateUserRequest` |
| 测试文件 | 与源文件同目录，`_test.go` 后缀 | `service_test.go` |

### 2.2 各 package 角色

| Package | 定位 | 职责 |
|---------|------|------|
| `packages/<领域>/` | 业务领域包 | 领域内的页面、组件、API、Hooks、类型；自包含，不依赖其他领域包 |
| `packages/shared/` | 跨领域共享包 | 通用 UI 组件、工具函数、全局类型；可被所有领域包和 app 依赖 |
| `packages/app/` | 应用入口 | 路由组装、全局状态、全局样式、构建配置；唯一引用所有领域包的 package |

> **关键约束：** 领域包之间**不允许互相 import**。`user` 不 import `order`。跨领域复用走 `shared`。只有 `app` 可以 import 所有领域包来组装路由。

### 2.3 领域包内部结构

```
packages/<领域名>/
├── src/
│   ├── pages/                # 领域页面（必选，至少 1 个页面）
│   │   └── <PageName>/
│   │       ├── index.tsx
│   │       ├── style.module.css
│   │       └── components/   # 页面私有组件（可选）
│   ├── components/           # 领域内私有组件
│   ├── api/                  # 领域 API 接口定义
│   ├── hooks/                # 领域 Hooks
│   └── types/                # 领域类型定义（index.ts 为入口）
├── package.json
└── tsconfig.json
```

| 目录 | 用途 | 可见性 |
|------|------|--------|
| `pages/` | 领域下的页面组件 | 被 app 的 router 引用 |
| `components/` | 仅本领域使用的组件 | 领域内可见 |
| `api/` | 调用后端接口的函数 | 领域内可见 |
| `hooks/` | 领域专属 Hooks | 领域内可见 |
| `types/` | 领域专属类型定义 | 领域内可见，对外暴露通过 `index.ts` |

## 四、deploy 部署目录规范

> 所有自动化部署相关资产统一存放于 `deploy/` 目录。
> 详细部署工具链与 Gokins CLI 配置参见 [部署规范.md](部署规范.md)。
> CI 平台流水线定义文件按平台要求放置，但实际执行的部署逻辑必须与 CI 调度配置分离，全部收敛至 `deploy/` 内。

```
│   ├── main.tf
│   └── variables.tf
└── scripts/                    # 部署辅助脚本（Go 单二进制工具优先）
    └── migrate.sh              # 数据库迁移等一次性操作
```

| 规则 | 说明 |
|------|------|
| ❗ 部署工具优先选用 Go 单二进制方案 | 使用 Gokins CLI 等工具，禁止依赖 Python/Node.js/Java 运行时 |
| ❗ 禁止使用 Ansible、Helm 等重型框架 | 用轻量 CLI 替代 |
| ❗ 本地调试直接用 CLI 命令 | 无需启动 Web 服务或配置账号密码 |
| ❗ Dockerfile 统一放 deploy/ | 不在 backend/ 或 frontend/ 各自存放 |
| ❗ 部署逻辑与 CI 定义分离 | CI 文件按平台要求放，部署逻辑在 deploy/ 内 |

## 五、强制规则

> 以下规则对标**《第一条 交付诚信原则》**，适用于所有 Engineer。

| 规则 | 说明 |
|------|------|
| ❗ 不可跳过分层 | Handler → Service → Repository，不得跨层调用 |
| ❗ 不得在 Handler 中写业务逻辑 | Handler 只做参数校验和响应封装 |
| ❗ 不得在 Repository 中写业务判断 | Repository 只负责数据存取 |
| ❗ 每个暴露接口必须有 API 文档 | 参照 OpenAPI 规范，文档不到位的接口视为未完成 |
| ❗ 关键业务逻辑必须有单元测试 | Service 层核心方法覆盖率 ≥ 80% |
| ❗ 所有 SQL 变更必须写 migration | 禁止手动改库，必须有 up + down 双向迁移 |
| ❗ 前端不得硬编码后端地址 | 统一从环境变量 / 配置文件读取 |

## 六、目录结构自动化校验

> 使用纯声明式的 conform 工具进行目录结构校验，禁止自研 Shell 脚本。
> 配置文件：项目根目录下的 `.conform.yaml`。

### 本地使用

```bash
# 通过 Makefile 统一入口执行
make check-structure
```

### 校验项（.conform.yaml 声明式定义）

| 校验维度 | 具体检查 |
|----------|----------|
| 顶层结构 | backend/、frontend/、docs/、deploy/、README.md、Makefile |
| Go 后端目录 | cmd/server/main.go、internal/module\|compositor\|middleware\|router\|config、pkg/、migrations/、config/ |
| 模块目录 | handler/service/repository/model 四个子目录齐全、根目录仅 wire.go |
| 模块命名 | 目录全小写、package 声明 = 目录名 |
| React 前端 | packages/app、packages/shared、领域包固定子目录结构 |

### CI 集成

```yaml
# .github/workflows/ci.yml
- name: Check Project Structure
  run: make check-structure
```

校验不通过 exit 1，CI 阻断合并。
